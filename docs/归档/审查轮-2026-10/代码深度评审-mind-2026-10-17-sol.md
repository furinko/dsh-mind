## 1. 结论先行

**架构方向值得保留，但关键治理承诺尚未形成端到端闭环，不宜把“测试全绿”当成可靠自治、独立复核或安全恢复已经成立。**

本轮收敛 **30 项问题：P1 17 项、P2 13 项，无已确认的宿主级 P0**。其中授权凭据/代录复核属于设计边界缺陷，不冒充新引入的代码回归。共执行 30 组隔离场景（含故障注入、时序屏障和正反对照）；另取得四次真实子代理创建失败。所有采纳的 P1 均由 Lead 读码交叉确认，能安全隔离的路径均补了真模块行为证据。

最应先处理：

1. **主权者事实与授权真实性**：自动消息可以解除失联；任意普通任务引用可充当任命依据；Lead 可用虚构复核署名批准自己。
2. **会审与返工完整性**：缺卷可采纳、揭卷后可改卷、打回中断可跳过返工、新代讨论继承旧预算。
3. **记忆的全局生命周期**：物理删除后并发晋升可复活原文；推翻的跨项目副本仍可召回；BOM 行可能“报已删除但字节仍在”。
4. **必需动作接线**：零分歧异常、探针见红后的恢复定位都只挂在可选动作；真实宿主子代理 API 已漂移。

本轮**不修实现、不改真实设置、不重启宿主、不提交 git**。仅新增本报告及证据包，原有 WIP 保留。

## 3. 整体设计评审

### 3.1 应保留的设计

- [Org 装配](<../../src/org.js#L50-L96>)显式注入依赖，组织动作集中在[动作表](<../../lib/actions.js#L253-L389>)，比散落在宿主回调里容易复核。
- [任务事件流](<../../src/tasks.js#L946-L1002>)与[纯工作台投影](<../../src/workbench.js>)职责分离；注册索引可重建；单文件写已有锁内复检和进程内串行保护。
- [两区载体](<../../src/paths.js>)把产品模板与部署数据分开；单包 exports + 裸包名客户端载体当前能闭合安装链。
- [调度设置服务](<../../components/kernel/lib/delegation-settings.js>)的 CAS、正式配置写回、持久态/运行态/接线态区分，比失联设置的旧保存链成熟；不应另造平行配置源。
- BM25 作为当前规模的检索默认值合理；本轮没有证据支持引入向量库或数据库来“修复”这些一致性问题。

### 3.2 六个结构性缺口

**① 权威事实不是普通记录。**

[设计](<../design/组织设计.md#L52-L71>)要求复核者由人确认，但[授权引用检查](<../../src/audit.js#L388-L407>)只证明“有这个任务”，[代录路径](<../../lib/actions.js#L465-L491>)只记录“Lead 声称这个人复核过”。哈希链能证明记录未变，不能证明内容真实、授权确由人作出、签署者确实参与。应明确采用“可信人侧授权事实 + 指向对象/动作/范围的引用”，还是承认这里只是可审计的代理陈述；两者不能混称。

**② 一个业务决定被拆成多笔没有恢复协议的写。**

单文件锁不能使“不过→关代→计数→升级”、晋升→删除、多区版本历史成为事务。现有“已落盘，别重试，人工核对”错误文案有价值，但不是恢复机制。应有操作标识、权威提交事件、幂等补账或操作日志；不必因此迁数据库。

**③ task epoch 没有贯穿所有消费者。**

任务图已有代次，讨论消息、预算、揭名冻结、汇总产物却未统一使用它；于是新代任务能消费旧代讨论，已经揭卷的答案还能被当前代覆盖。需要一份跨任务/消息/投影的 attempt 契约，而不是每个入口再补一个 if。

**④ “必须发生”仍寄托在可选调用上。**

零分歧入账与恢复定位的函数都在，也都有测试，但主环路不保证调用。应从权威状态转换触发，并提供幂等读数；否则工具存在不代表机制运行。

**⑤ 可见性不是删掉某个字段。**

工作台、任务响应、总线、聚合检查各有自己的遮罩，顶层产物和聚合判断绕过了局部遮罩。应给每种读者与任务阶段定义统一 DTO 可见性，再枚举所有可达读面验证。

**⑥ 宿主契约与部署制品缺少可追踪版本。**

插件当前[兼容声明](<../../package.json#L58-L67>)没有限制已验证上界，测试假宿主仍提供旧 API；探针版本又只认 `boot` 或声明哈希。应绑定具体宿主契约代次、包/构建指纹，并有真调用式契约冒烟，而不只是 import 成功。

## 7. 不混入缺陷计数的设计决策与盲区

### 7.1 应明确拍板的边界

1. **主权者授权/复核代录的信任等级。** 若继续由 Lead 自己记授权和代录结论，应承认它是“可审计代理陈述”，不是对不可靠 Lead 的机械制衡。若要后者，须增加独立可信人侧/签署事实，不能只加更多文本标签。
2. **撤回岗位是否停用现有实例。** [拒名单判定](<../../src/policy.js#L948-L953>)仅看对象 id 与主体 id，不查主体的岗位。隔离里撤回“插件工程”后该岗成员仍可写知识。若撤回仅禁止改卡，这是当前实现；若意味着撤销岗位资格，则需传播到实例判定。本项因语义待决，**不重复计为无条件 P1**。
3. **安全边界到哪里。** 在本机会话仍有宽文件/命令能力时，插件动作闸不是 OS 沙箱；不能声称它能阻止同权限进程直接改文件/授权真源。本轮没有为了证明这一点去改真实受保护文件。
4. **项目键是否允许同名目录。** 目录 basename 是现行设计，两个不同根的同名目录可能共项目；这是需明确的产品选择，不以本轮偏好擅改。
5. **衡量组织价值。** [立项目的](<../design/组织设计.md#L19-L31>)是同类问题成本下降、知识不只涨不用。现有计数/审计是运转证据，不是该目的的成效证据。建议用少量真实复发/复用案例追踪，不急着造复杂评分或热度系统。

### 7.2 本轮未验证

- 真浏览器/桌面像素、CSS布局、无障碍、真实React调度差异。
- 真实人侧POST、认证攻击矩阵、真实授权撤回与当前profile热装配。
- 宿主重启/冷启动后逐项真触发；真实 npm tarball 安装和发布。
- 多进程锁竞争、进程强杀/断电、磁盘满、长期规模性能与检索真实回归集。
- 全仓系统性变异测试；本轮使用的是定点反例和对照，不冒称所有门禁均已证明判别力。
- 提前停用的成员未提交部分；没有将其未回报的猜测写成发现。
