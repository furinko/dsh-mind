## 1 目标的建立

用户明确表达需要持续推进的结果时，可以据此建立目标，不要求用户为同一意图再确认一次。目标保留对应意图的来源引用，便于后续核对约束与变更。

普通问答无需全部登记为长期目标。Lead 可以提出新的目标建议，但建议不会自行成为用户的长期承诺；任务拆分也不能借机扩大目标范围。

## 2 最小信息

| 信息 | 内容 |
|---|---|
| 期望结果 | 用户最终希望得到什么 |
| 约束 | 范围、重要限制及已有授权的引用 |
| 完成依据 | 用什么观察或交付物判断结果达成 |
| 关联任务 | 为该目标执行的任务引用与必要关系 |
| 关键决定 | 用户或有权主体作出的取舍、调整及其来源 |
| 下一步或等待原因 | 当前可推进的工作，或缺少的材料、结果与决定 |

目标状态另行明确表达。目标上的任务进度由关联任务图重算；已有事实通过引用使用，避免复制出第二份可独立修改的任务状态。

待验证判断与已确认事实分开呈现。关键决定属于目标的持久记录，任务执行细节与知识正文保留在各自的权威记录中。

### 目标变更与执行调整

| 变化 | 依据与处理 |
|---|---|
| 目标变更 | 用户调整期望结果或硬约束，保留变更来源和历史 |
| 执行调整 | Lead 在既定目标与有效授权内换方案、拆任务或调整顺序 |
| 权限变化 | 新增读写范围或外部副作用，按现行授权规则处理 |

用户在对话中的明确调整可以成为变更来源，不为同一意图重复要求确认。Lead 的执行调整不能自行改写用户目标或扩展授权；已有有效授权可以沿用，授权缺失或失效时说明具体缺口。

目标变更后，已有任务、成果和证据继续保留。是否满足新目标应重新核对；已经冻结的任务判据仍按原机制处理，需要不同交付时通过合法承接或新任务推进，不给旧执行者补签新结果。

## 3 五种状态

| 状态 | 判定含义 |
|---|---|
| 进行中 | 存在可以在当前授权内推进的下一步 |
| 等待 | 当前没有可推进的工作，需要材料、外部结果或用户决定 |
| 暂停 | 用户明确要求暂不推进 |
| 完成 | 完成依据已有实际证据支持 |
| 取消 | 用户撤销目标，已有事实与责任记录保留 |

一个子任务受阻，不自动使整个目标等待。其他工作仍可合法推进时，目标继续处于进行中，并列出受阻部分。

暂停或取消保留已经发生的执行事实与副作用。如何停止正在执行的操作，以及到达什么安全停点，由后续执行机制规定；状态变化不代表世界已经回滚。

## 4 推进与完成

目标通过一项或多项任务逐步推进。Lead 可以在既有意图和授权内拆分任务、调整顺序或更换执行实例，仍须遵守任务本身的冻结判据、绑定、复核与采纳规则。

每个进行中的目标应给出可执行的下一步；如果缺少合法推进条件，明确进入等待并说明原因。等待需要什么信息或决定应具体可理解，避免只显示一个笼统的阻塞标记。

任务全部结账只是完成判断的输入。目标完成还要核对用户期望结果、约束与实际证据，不能用任务数量或流程结束代替。

客观可验证的结果，在已有授权内依据证据验收。涉及用户偏好或取舍、无法用客观证据判断的部分，交由用户决定。目标的完成记录引用实际证据，不把待验证判断写成完成事实。

## 5 跨会话摘要与工作上下文

交接生成一份简短工作摘要：目标、约束、已完成部分及证据引用、未解决问题、下一步或等待原因。新会话按需读取原始证据、关联任务、关键决定和适用知识。

摘要是可重建的读面，不承担第二份权威状态。摘要与当前任务事实冲突时，以任务真源和有来源的目标决定重新生成；没有证据的判断仍标为待验证。

会话关闭、实例封存或岗位调整，不自动结束目标。接续者保留历史署名与证据，只对自己的执行负责，不替旧实例补签完成。

### 默认加载与按需读取

| 方式 | 内容 |
|---|---|
| 默认加载 | 当前目标、硬约束、本次任务、验收依据，以及当前身份必须遵守的授权和规则 |
| 按需读取 | 与下一步直接相关的证据、知识和岗位规程、能力正文 |
| 保留引用 | 详细历史与原始记录，核对细节时展开 |

必要授权、硬约束和强制规则始终适用，不能因相关性排序或内容预算被静默省略。未验证资料可以作为本次探索的输入，但其判断状态与来源应明确，不能装配成已确认知识。

目标、环境或版本变化后，重新判断知识是否适用；已被推翻或失效的结论不作为当前有效建议，调查历史时仍可按权限读取。上下文规模受本次工作预算约束，具体分配规则在执行接口中设计。

### 持续工作的逻辑循环

```mermaid
flowchart LR
    A[目标与约束] --> B[选择下一步]
    B --> C[装配所需上下文]
    C --> D[授权内执行]
    D --> E[验证成果]
    E --> F[更新进展及知识候选]
    F --> B
```

该循环描述一次已受理工作的推进关系，具体操作仍遵守任务图与授权规则。进展引用真实任务和证据；知识候选在具备资格后按原晋升规则处置。

## 6 执行授权与后续接口

保存目标与进展不自动授予副作用权限，也不自动启动后台持续执行。新会话接续时按当前身份、任务绑定和有效授权判定，历史获准不能替代当前资格。

推进与等待、事件唤醒、目标共用预算、执行归属及通知原则见[持续执行与预算](持续执行与预算-2026-10-20.md)。这些原则用于约束后续接口，具体后台配置和执行调度仍需单独实现与验证。

下一阶段需一起设计以下执行接口，避免各自形成状态真源：

- 目标如何关联任务、持久记录范围变更，以及处理已完成目标的新请求。
- 多个 Lead 如何选择可推进任务、处理并发更新和完成判断冲突。
- 等待条件如何被观察，何时唤醒执行者，以及调用、时间和费用预算如何约束执行。
- 暂停与取消如何停止新增推进并处置运行中的操作，如何记录部分完成和不可逆副作用。

这些接口的实现与第一批工程修复分开验收；第一批仍聚焦成员工具边界、产物票绑定、任务账本完整性与项目身份隔离。
