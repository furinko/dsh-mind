## 一、高严重度（P1）

### A. 信任链与权限核心

**P1-1 主体身份无凭据层，最高权限完全信任自报**（结构性）
- [src/subject.js:75-79](../../src/subject.js#L75-L79)：会话 header 无 `origin:'subagent'` 且无 `delegationDepth` ⇒ 直接判 Lead。注释自认「未在真实运行态验证、fail-open 残留面」。宿主升级/新会话路径不写这两个字段，成员子代理即得 Lead 全权。
- [src/policy.js:452-459](../../src/policy.js#L452-L459) + [policy.js:916](../../src/policy.js#L916)：身份对账只覆盖 成员/复核者；主权者/Lead/出厂作者/系统 的 kind 原样采信，无任何档案或凭据验证。「策略引擎是唯一判定点」的根信任锚是「调用方不会说谎」。
- 组合后果：任何未来新增调用点把模型可控数据拼进 subject，即穿透整座权限大厦。actions.js 门①/门②正是在事后补这类历史洞——说明这个威胁模型已被验证过。

**P1-2 宪章不变式 fail-open：proposerId 缺席 ⇒ 自批检查静默跳过**
- [src/policy.js:522](../../src/policy.js#L522)：`action==='approve' && context.proposerId && ...`——context 由调用方拼装，漏传 proposerId 则 §3.4「不得自批」整体不生效。应改为 approve 时 proposerId 必填（缺席即拒）。一行可修。

**P1-3 grant 层三重 fail-open**
- [src/policy.js:688-700](../../src/policy.js#L688-L700)：`verdict ?? 'allow'` 且只认 `'deny'`/`'confirm'` 精确值——把 deny 写成「拒绝」/"Deny" 即变显式放行。
- [src/policy.js:490-496](../../src/policy.js#L490-L496)：求值序 grant → tierRule → scopeOf：一条宽 grant（不限定 kind/authority/target）可在任务边界检查之前 return allow，成员无需任务上下文即获全局写权；法律件一行 grant 可凌驾宪章档默认。
- [src/policy.js:682-701](../../src/policy.js#L682-L701)：首条命中即返回、无 specificity 排序，授权结果取决于文本书写顺序；grants 还完全不看 target.id/zone/domain。

**P1-4 scopeOf 空负责人 ⇒ 任意成员任务内全权**
- [src/policy.js:316-319](../../src/policy.js#L316-L319)：`名单.length===0 ⇒ {ok:true}`。负责人为空的节点（解析失败/手编/旧数据）对全员开放「任务内全权」。与全文件 fail-closed 口径相反。

### B. 并发与崩溃一致性

**P1-5 withLock 双缺陷：强夺分支不可达 + 强夺路径 TOCTOU**
- [src/kernel/fsx.js:170-171](../../src/kernel/fsx.js#L170-L171)：默认 `staleMs=60s > timeoutMs=10s`——等待者 10s 先超时抛错，强夺分支永不可达。崩溃残留锁文件使所有 registry 身份变更（[registry.js:484](../../src/registry.js#L484)）持续失败，需人工删锁。2026-10-12 上调 staleMs 时未同步 timeoutMs。
- [src/kernel/fsx.js:210-217](../../src/kernel/fsx.js#L210-L217)：强夺路径 stat→rm 无重校验，跨进程可双入临界区（进程内被 serializeByKey 兜住，跨进程无兜底）。

**P1-6 任务状态机检查系统性在锁外（TOCTOU）**
- [src/tasks.js:601-608](../../src/tasks.js#L601-L608) `#requireTransition` 基于锁外读；[tasks.js:484-512](../../src/tasks.js#L484-L512) 仅 reassign/reject/create依赖/submit讨论段 四处锁内复检。攻击例：review(过) 与成员 submit 并发 ⇒ 已采纳节点被洗回「已交卷」并替换独立答案；并发双 review 终态由落线顺序决定。锁内复检（eventBuilder）模式已在四处验证可行，最小修法是把 #requireTransition 整体挪进锁内。

**P1-7 审计账本两类损失不可检测**
- 撕裂行静默漏报：[src/kernel/fsx.js:86-100](../../src/kernel/fsx.js#L86-L100) readJsonl 跳过坏行且无报告通道，而 [audit.js:274-354](../../src/audit.js#L274-L354) verify() 复用同一读取器——崩溃撕裂的半行被两边一起跳过，verify 全绿，记录永久丢失。
- 整月成对删除：账本与锚同目录同为普通可写文件（[paths.js:247-249](../../src/paths.js#L247-L249)），months() 仅枚举现存文件——删掉整月 jsonl+anchor 后该月消失，verify 照常全绿。链哈希只护链内行，无链外月份清单/跨月检查点。§3「审计日志不可逆」有实质缺口。

### C. 机制失效

**P1-8 零分歧报警（§10 核心反趋同机制）近乎恒不触发**
- [lib/actions.js:682-683](../../lib/actions.js#L682-L683)：`review_zero` 的结论集完全自报，不从任务图独立答案重算——Lead 递假反例面即可压掉报警。

**P1-9 归档作答可读性矩阵可绕过**
- [src/memory.js:349-352](../../src/memory.js#L349-L352)：`显式:true` 且不传 `读者` ⇒ 归档检查的第二个 if 因读者为空直接跳过——任何成员带 `显式:true` 即可读归档作答。一处 if 顺序即可闭合。

**P1-10 同源路由防线只防浏览器，本机任意进程可伪造主权者设置**
- [components/kernel/lib/routes.js:90-116, 185-231, 238-249](../../components/kernel/lib/routes.js#L90-L116)：同源检查依赖 `sec-fetch-site`/`Origin`——curl/本地进程不带这些头全放行。可 POST presence 改失联限制/响应期限（审计主体恒记伪造 `{id:'设置页',kind:'Lead'}`），GET workbench 以 Lead 视角取全量投影。唯一缓解是绑 localhost。

**P1-11 `派生自`/`同锁追加` 内部通道在服务面暴露**
- [src/memory.js:151,161,927](../../src/memory.js#L151)：注释声明「调用方不传」，但 remember 签名接受且零校验——外部传 `派生自` 可伪造推翻替换链（血缘事实变自报），传 `同锁追加` 函数可向账本追加任意构造行。防线全在上游 handler 不透传。

**P1-12 debate.open 编排非原子**
- [src/debate.js:57-148](../../src/debate.js#L57-L148)：reveal→pickDissenter→debateOpened 无锁无补偿。失败时反对者指定已入审计 ⇒ [review.js:324-330](../../src/review.js#L324-L330) 永久烧掉该候选（反趋同资源泄漏）；并发双 open ⇒ 轮次重置为 1。

**P1-13 purge 三步化并发下漏隔离**
- [src/memory.js:590-618, 847-864](../../src/memory.js#L590-L618)：闭包基于无锁读的血缘索引；闭包算完后、抹除前的并发 remember 可写入引用该源的新条目——不进隔离清单，源被抹后悬空血缘逃逸 §C8「下游隔离」承诺。

**P1-14 披露正则 ReDoS 通道**
- [src/memory.js:786-794](../../src/memory.js#L786-L794)：部署.json 披露敏感模式只校验「可编译」不校验灾难性回溯；`(a+)+$` 类可通过，单次晋升的 `re.test` 即可阻塞事件循环。每次晋升还重复编译无缓存。

## 四、设计层面结构性问题（跨模块）

1. **信任锚缺失凭据层**（P1-1 的根）：整套权限体系的最高身份（主权者/Lead）是「自报+宿主诚实」模型。要么补一个宿主签发的会话凭据，要么在引擎层维护结构性身份登记——否则每新增一个调用点都要靠动作层门①②③事后补丁。
2. **防御纵深只活在动作层**：bus 发件/全员已交、盲评遮罩、线程闸、结论集全在 lib/actions.js 补——服务面（src/*.js）本身零防御。历史 P2 漏口正是「服务面裸奔+新调用者接入」长出来的。建议把关键不变式下沉到服务层（与动作层同口径），动作层只做入参归一。
3. **「只增」的完整性保证不均匀**：审计链有哈希链但撕裂行/整月删除不可检测（P1-7）；记忆账本/任务图事件流/探针快照完全无完整性机制。要么统一最底线（坏行可见+链外检查点），要么在设计文档里明确降级哪些面是「信任本地文件系统」。
4. **跨文件字符串协议互锚**：齐卷判据、盲评遮罩、预算名单、轮边界（ROUND_BOUNDARY_MARK）等不变式散在 tasks/debate/review/bus/actions 五个文件，靠注释约定对齐，无模块级强制——每次扩展都在漂移边缘。
5. **默认值倒向宽松侧的系统性倾向**：proposerId 缺席跳过、grant 非 deny 即 allow、介入度坏值回退最宽档、空负责人放行、归档读者为空跳过检查——五处独立代码犯了同一方向的错误。这不是能力问题，是编码规约问题：**缺席/坏值在判定面必须倒向拒绝**。建议加一条 lint 级约定并全量自查。
6. **可维护性**：policy.js 59KB 六职责、lib/actions.js 63KB、board client.js 198KB（另有 214KB harness）单文件；结构校验、锁、审计、策略解析互相缠绕。变更面高度集中（本报告 P1 有 8 条集中在 policy.js + fsx.js 两个文件）。
