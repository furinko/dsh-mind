## 一、总评

**这是一套罕见地把「治理」当第一性问题来设计的 LLM 组织系统**——判据驱动、事件溯源、fail-closed、反趋同、留痕文化，五条主轴在代码里的落地密度高于绝大多数同类系统（含商业系统）。设计文档有哲学、有自洽性论证、有修订记录与采纳率记录——**设计过程本身可审计**，这一点本身就是示范级的。

但它当前有三个**结构性张力**，全部指向同一句话：**机制供给远超度量与采纳**。

| # | 张力 | 一句话 |
|---|---|---|
| 1 | **治理密度 vs 单用户现实** | 为多成员组织设计的制衡机器（会审/盲评/反对者/零分歧报警），运行形态是 1 主权者 + 1 Lead + 易失成员；触发率低而维护成本全付 |
| 2 | **成败判据无度量** | §1 定义了「成 = 同类问题解决成本随时间下降；败 = 同一个坑踩第二次」——但全套系统没有任何机制在**测量**它 |
| 3 | **采纳成本盲区** | 身份链解决了「成员是谁」，没解决「成员怎么知道该干什么」；评审者本人（Lead）今天就绕行了全流程（§9.4 实录） |

## 二、设计目标达成度（§1 三条立项理由）

### 理由 1：长期记忆 —— 部分达成，且学习闭环走了设计外路径【实测】

7 天运行数据（2026-10-15 读数）：记忆 60 条 = 经历 47（78%）+ 知识 10（17%）+ 偏好 3（5%）+ **作答 0**；知识晋升 **0 次**；自治能力卡 10 张（出厂 6）。

三个观察：

1. **经历条目质量极高**——每条都是带复现步骤、原始回执、教训提炼的事故报告（BOM 事故、面板视觉三轮纠错、复核员闭环首跑……）。这是这套系统最有价值的产出物。
2. **真正的学习闭环是「经历→能力卡」**：10 张自治能力卡（assert-with-evidence、no-life-inference-from-permission、grounding-before-claim……）几乎全部从事故中长出来，且 `1amwx` 节点实证了「同型错误复发即升级能力卡」这条纪律真的在运转。**而设计文档规定的正式路径——知识晋升（Lead 判定跨项目可复用→追加岗位标签）——7 天 0 次**。学习在发生，但走的不是设计的那条路。
3. **作答类记忆 0 使用**：会审独立答案实际存在任务图事件流里（`submitted` 按人留卷），不经过记忆服务的作答类。设计里的四类分类学，实践中收缩成两类半。

> 【判断】知识晋升 0 次不一定是设计错误——7 天太短、单项目部署下「跨项目可复用」判定天然少触发。但「作答类闲置」是设计与实现的真分歧：要么把会审答案归档接进作答类（设计的本意），要么承认任务图事件流就是作答的载体、删掉这个类。

### 理由 2：避免上下文污染 —— 达成度最高的一条【实测+底稿】

项目隔离（目录边界）、按需拉取（上下文 = 岗位知识+任务节点+本轮线程+按需检索）、总线历史不入上下文、审计三级分档（全记/记汇总/不逐次记）——四件全部落地且有测试钉住。

**唯一的自伤**：workbench 全量投影实测回传 **~117KB**（本次评审亲测，被截断落盘）且无条数上限【实测】——读面本身成了上下文污染源。给人的看板（分页/折叠/轮询）与给 LLM 的读数（紧凑摘要+按需展开）没有分离。

### 理由 3：减少讨好效应 —— 机制完整，一次全链实证，但边界外无效【实测+文档】

- 机制群（盲评/揭名/强制反对者/零分歧报警/结论层结构化/Lead 不首发）全部实现，2026-10-14 **完整跑通过一次全链**：提名→常任授权→spawn 两名复核员→三单独立复核→三态全过→死代封存。最有说服力的读数是：**「指令无效条款」咬了它的作者两次**——两名复核员把 Lead 后勤指令里的放宽空间按条款记录在案并拒绝采纳【文档：exp-经历-…-711a2c】。机制对内建它的人同样生效，这是独立性的实证。
- **但反趋同的覆盖边界 = 策略引擎的边界**。Lead 走编外通道（裸 subagent）时，盲评/反对者/零分歧/提审分离全部不适用——本次评审的四线深读就是这样发生的（§9.4）。组织的边界不是宿主的边界，设计对此无表述。

## 三、概念模型评审

### 3.1 骨架是对的，且被代码忠实执行【底稿】

**三形态分离**是全套设计最闪光的骨架：

| 形态 | 承载 | 代码验证 |
|---|---|---|
| 事件流 = 状态权威 | 任务图 18 种事件单遍 fold（tasks.js:1059-1201） | 写路径锁外预检+锁内复检双重闸约 15 处 |
| 投影 = 无存储 | workbench 纯函数零 IO（workbench.js:4-6） | 技术上保证不做第二事实源 |
| 索引 = 可重算 | registry index.json、记忆血缘纯内存投影 | 重启重建，不另立真源 |

配套的三个决策同样正确：**待决项 = 节点状态**（不设第二队列）、**产出物只存引用**、**授权是标签不是路径**（判定只读标签——策略引擎直读 identity.json 而不 import registry，刻意避环，policy.js:357-364 有论证）【底稿】。

### 3.2 概念模型的实践磨损【底稿+实测】

1. **岗位名硬编码散布**：`'复核员'`/`'Lead'`/`'主权者'` 字符串遍布 policy/registry/org 多文件，无单一常量源——主体种类有封闭清单，**岗位名没有**。改名即多文件手术。
2. **zone 词汇三套**：`'私有'`（policy.js:787）/`'自治'`（registry.js:32-35 键）/`'自治'+'出厂'`二分（upgrade.js:253-254）——行为靠 Layout 的 else 语义兜住，但词汇漂移是「改一处忘另一处」的温床【底稿】。
3. **kind 封闭清单 11 种 vs 实际使用**：作答类 0 使用（§二）；`产物` kind 的正文写入面（store.write）曾长期零生产调用（设计债②，现已由 capability_publish 兜网）。
4. **复核者的「只读命令白名单」是纸面件**：`readonlyCommand` 无运行时调用点（设计债①在案），且底稿发现白名单是**整串/前缀匹配**——`find / -exec <任意命令>` 以 `find ` 开头即放行、`git diff --output=` 可写盘（review.js:404-406）【底稿】。若将来接线，必须连执行语义一起设计，否则是负资产。
5. **kernel 与 guard 是两套平行入口纪律**：guard 的 `runGuardAction` 独立 switch，不经 runAction 的门①（role 自报拒绝）/门②（主体必填）/身份对账——「装哪个组件有什么动作是字面事实」的代价是**入口防线各自实现**（当前守住了，guard index.js:128-134 记录了修前硬编码 Lead 的漏洞），任何新增 guard 动作都要记得复制这套纪律【底稿】。这是概念模型「组件可独立启停」与「唯一判定点」之间的结构性张力。

### 4.1 fail-closed 链条：全套最扎实的部分【底稿+实测】

### 4.3 残留 fail-open 清单（按危险度排序）

1. **结构性身份无凭据层**：`kind:'Lead'`/`'主权者'` 由结构采信，引擎对最高身份无第二道防线【文档：P1-1 结构面，裁决维持+挂账】。这是整个信任模型的根——当前靠「宿主注入主体+会话事实」双门撑着（债⑳已取证：本机宿主根会话=Lead、子代理=成员，未触发 fail-open）。
2. **markInteraction 无策略闸**（registry.js:424-430）：失联时钟的解冻完全依赖调用方纪律，任何持有 Org 引用的代码路径都能重置失联【底稿新发现】。若宿主事件语义变化（子会话消息也算 user/message？），失联保护静默失效。
3. **路由写面本机无凭据**（routes.js:44-46,177）：设置页主体 `{id:'设置页',kind:'Lead'}` 且允许无头本机读——本机任意进程可改失联设置/读全量投影【底稿；代码已如实标注为主权者级权衡】。
4. 工具总范围未配置=放行（有启动告警，裁决乙在案）【文档】——语义是「主权者没设=无限制」，接受。
5. `identityStatus` 缺 status 字段按「在岗」放行（policy.js:1194-1197），而 `#档案岗位Of` 要求严格==='在岗'（:369）——手改档案删 status 字段时两种口径【底稿新发现，低危】。

### 4.4 并发正确性：审计链之外的账本仍在已知竞态下裸奔【底稿新发现】

fsx.js:302-309 明文承认 Windows 名字式文件锁有 rm/create 竞态（审计链曾因此 fork），**审计账本补了 serializeByKey 进程内第二层，任务图（tasks.js:860）与总线（bus.js:92/260）没有**。同一竞态对 tasks.jsonl 意味着可能的双行事件，且任务图没有审计链那样的自检兜底。配套发现：debate 三事件不在 TRANSITIONS 表内、齐卷判定只在锁外（debate.js:62），与 review(过) 并发可在已采纳节点上开出活跃讨论段【底稿，P1 级】。

### 5.2 两条设计层评价【判断】

1. **预算闸把人类会议规程完整搬给了 LLM**（每轮消息数/每人字符/快照冻结/轮边界系统消息）——实现完成度极高（16+ 测试钉着）。但其触发频率与维护成本的比率从未被测量。这套机制的存在合理性当前靠哲学论证（§10 对应立项理由 3），不靠数据。

## 六、记忆与知识管理评审

### 6.1 设计的精致与实现的收缩

四类分类学+双标签归属+血缘闭包+披露闸+物理删除三步化+粘性否决——设计精细度是学术级的，实现也全落地（契约 A/B/C 三批全绿）。但实践数据（§二）显示：**经历占 78%，作答 0，晋升 0**。分类学在实践中收缩。

【判断】收缩的根因不是实现差，而是**分类的判定成本落在 Lead 头上**：写知识要判「跨项目可复用」，晋升要 Lead 显式追加岗位标签——每一步都是人工决策点。而「经历→能力卡」的闭环之所以活，是因为它有**自动触发器**（同型错误复发即升级）。设计教训：**记忆分类学需要触发器，不能靠分类判断**。

### 6.2 本次评审抓到的两条现场活 bug【实测】

1. **`memory_query` 带 `类` 参数即崩**：`{action:'memory_query', 类:'知识', 文本:'…'}` ⇒ `wanted.join is not a function`（裸 TypeError，非结构化拒绝；复现两次；去掉 `类` 参数即正常）。`类` 是工具 schema 里登记的合法枚举参数——**schema 承诺的参数把动作打崩**，且错误穿透了「拒绝必须结构化」的纪律。P1 级。
2. **status 用错项目（根因已钉）**：status（07:24）报「项目 default / 任务 0 / 知识 0 / 合计 50」，workbench（07:37）报「项目 repos / 任务 31 / 知识 10 / 合计 60」——**status 是拿 default 项目的组织在回答 repos 项目的调用**。根因链：内核 apply() 时 `shareOrg` 装配一次（project=default，kernel index.js:49）→ mindTool 每次解析本次项目（:244）传给 runAction → 绝大多数 handler 把 `项目` 线进服务调用（workbench/query 均覆盖 `spec.项目 ?? this.project`）→ **`status({ org })` 不接项目参数**（actions.js:351），`org.status()` 用装配时的 `this.project`（org.js:262/267/270）。两次读数各自都「对」，错的是 scope。与 649a4（任务上下文透传断链）同族：**动作层参数透传普查**是系统性修法。附带：内核提示段 `项目键：${org.project}`（kernel index.js:577）同样用装配期项目。P1 级。

### 6.3 底稿补充的记忆层设计债【底稿】

- 「最新 N 条」措辞 vs 实际语义（账本扫描序最后 N 条，非按记于时间）——跨类查询时偏差明显（数据线 E4）。
- fold 状态回放按秒级时间戳排序，同秒内非否决族状态次序可乱（E6；粘性判据只护住否决族）。
- purge 是 O(下游数 × 全库行数)（#folded 无按 id 索引，逐 child 全库 fold——F1）；stats 绕过行缓存全量重读（F3）。
- readableBy/stats/activity 三个读面无 policy.check 无审计——与契约 B「只读面收窄」形成口径空洞，代码未写明豁免依据（C2）。

### 7.1 双区载体与条款级合并：设计完整，实现忠实【底稿】

「不许『等其他类似情况』兜底」的封闭清单 + 「红线内容归主权者、防护机制存在归出厂作者」的切法，是对「安全机制无限扩张」的正确约束。**恒绿报警本会话实测触发**（status 与审计账本均见「探针健康异常：恒绿的灯等于没灯」告警）——2026-10-13 裁决第二批 P2-10 的接线真实生效。

### 7.3 审计链：全部模块中最扎实的一件【底稿】

逐月独立链 + 每月锚点原子重写（防砍尾）+ 跨月更正声明全局表 + 撕裂行体检 + 写侧 JSON 往返归一（2026-10#37 事故的产物）——一套自洽且**自知边界**的防篡改设计（首尾月截断、崩溃窗口都如实登记）。

### 7.4 设计文本与现实的漂移——没有回改机制【文档+判断】

《组织设计.md》§4 仍写自动回滚是「**策略引擎内置行为：无条件执行**」；裁决甲′（2026-10-09）后现实是「只定位+无条件入账+告警升级主权者，运行态不自动改文件」。DESIGN-MAP 如实记录了新口径，但**设计文档本身从未回改**——v1.5 定稿后，五轮裁决的实际演化全部散落在裁决文档里。同类漂移还有债⑳降级口径、探针五道配套的措辞变化。

【判断】这套系统对**代码**的漂移管理是示范级的（DESIGN-MAP 接线状态纪律、塞 bug 校准），对**设计文本**却没有同等机制。设计文档正在变成「历史文物」而非「现行宪法」。建议：裁决落地时同步回写设计文档并版本化（复用既有版本历史机制即可），否则下一轮设计评审的对照物就已经错了。

## 八、面向 LLM 的可用性评审（调用者视角，全部亲测）

### 8.1 好的部分

- **错误消息可执行性一流**：五字段结构（规则/理由/要什么授权/怎么改）+ howToChange 全链贯通。本会话两次被拒（探针身份拦截），照着拒绝消息就能走下一步——这是设计承诺「拒绝必须带可执行理由」的真实兑现。
- **审计分级**真的在控制噪音：成功调用按轮桶汇总、失败全记（我的 glob 失败、send_message 失败都在账上，每条一行不刷屏）。

### 8.2 坏的部分

1. **41 个动作 + 58 个扁平参数**，其中 11 个无 description；中英文参数混排（project/role/limit vs 实例/描述/条数上限）；`memory_query` 同时收 `limit` 与 `条数上限`；`id` 一参跨 ~20 个动作语义不同（任务 id/记忆 id/待决 id/能力 id）【底稿】。对 LLM 调用者，这是每会话都要重新学习的 API 面。
2. **大读面无上限**：workbench 全量 ~117KB 一次性回传【实测】，且统一走 `JSON.stringify(…, null, 1)` 缩进打印，token 成本再放大 ~1.5-2×【底稿】。紧凑档（给 LLM：计数+待决+异常）与完整档（给人/看板）不分离。配套：workbench 审计条数动作面默认 20 vs 路由面看板包固定 40 vs audit_tail 又是 20——三个数三种出处【底稿】。
3. **降级态不对称**：组织装配失败时，模型侧有降级自述工具（degradedTool 回报失败原因与修复指引），人侧连 `/mind` 命令都没有——人没有等价的「组织为什么没起来」入口，只能翻宿主日志【底稿】。
3. **schema 承诺的参数会打崩动作**（§6.2 F1）、**两个读面答案不一致**（§6.2 F2）——可用性问题的最重形态：调用者无法信任自己的工具。

### 8.3 INTERFACES.md 声明面漂移【底稿】

RoundRecorder/entryFingerprint 声明了但 src 零匹配（轮桶实际在 kernel 内存 Map）；review.nominate/bus.unlock 签名漂移；registry.restore 有实现无入口；整个 525 行同源路由面（routes.js）零记载。「登记的 API ≠ 可用的 API」是 10-14 报告点名的系统性问题，修复后又长出了新的。

**对照面值得一提**：README 的动作清单（41 项）、命令面专属动作、guard 六动作，与代码**逐项核对零漂移**【底稿】——动作面声明维护得极好，漂移全部集中在 INTERFACES.md 的 src 层签名。这说明漂移不是态度问题，是**没有「签名从代码生成」的机制**：手工同步的面在维护，机械生成的面没有。

## 九、复杂度与采纳成本评审

### 9.1 复杂度热点【底稿】

- memory.js 1406 行五职责（服务/fold/血缘/缓存/披露/物理删除）——数据线最大汇聚点。
- tasks.js 1214 行：18 case fold × 11 操作 × 双重闸——**本插件复杂度的主引擎**（正确性收益真实，但每加一个事件三个面都要动）。
- actions.js 1208 行：presence 设置读写（~90 行含锁/原子写）与 registry_list 活动索引（O(审计规模)/次）长在「动作表」里——路由层过厚。
- O(历史) 读面清单（#folded/#verifyRefs/#taskExists/#轮派/autoRollback/授权依据存在）——触发器设定合理（万行级），但 board 3s 轮询 × stats 绕缓存会先到。

### 9.2 维护性悖论【实测+判断】

7 天内：6+ 轮审查/修复迭代、4 份审查报告、20+ 条裁决、534 条测试、塞 bug 校准数十次。**产出质量无可挑剔**（测试文化是本仓最硬的资产），但这本身证实了张力 2：**治理开销是真实且沉重的，而收益侧（同类问题解决成本下降）没有任何读数**。这套系统现在不能回答「它自己值不值」——不能回答的原因不是答案是否定，而是**没有测量**。

### 9.3 Windows/NTFS 绑定【底稿】

EPERM=锁被占、线程等价键只折大写对齐 NTFS 比较表、保留设备名拒绝——单平台假定；迁到大小写敏感文件系统时线程等价键方向是误合并非放行。配套：fsx 全程无 fsync——rename 原子性保护「读者看不到半文件」，不保护掉电后内容仍在，对「审计是不可逆凭据」的定位是已知未处理的耐久性窗口。

### 9.4 评审者绕行实录：采纳成本的一手证据【实测】

本评审启动时，Lead 面对四线并行读码，**没有走组织自己的派活流程**（定判据→建卡→registry_assign→task_dispatch），直接用了宿主原生 subagent。事后实验把因果链钉死：

| 层 | 结论 | 证据 |
|---|---|---|
| 硬约束 | spawn_teammate（Agent Teams）需用户显式点名——堵死一条路（但不是唯一路） | 会话指令 |
| 身份闸 | 子代理有 mind 工具，未登记一调即拒（fail-closed 生效，拒绝消息自带修法） | 探针×2 + 账本 seq635 |
| id 桥 | subagent 工具 id = mind 实例键（逐字节配对）⇒ registry_assign 机械上可对接 | 配对实验 853d4545 |
| 归属 | **无机制借口——是 Lead 自己的成本权衡** | —— |

更深的发现是**协议上下文缺口**：即使登记成功，成员子会话对组织协议一无所知（派活流程/主干环路/怎么交卷），这些只注入了根会话；设计 §7「岗位知识随身份带」在宿主侧**没有机械载体**。每起一个成员，Lead 的 prompt 工程成本重付一次。2026-10-15 的派活闭环裁决（提交 7528ca2：派发闸校验负责人就位+内核提示段常驻提醒）已认领了一半（「派给空气等于派了个名字」），且明确记录了「宿主 Agent Teams 指令默认抑制拉人，与组织期望相反，两边互不知晓」——**组织与宿主的指令层互相不知道对方的存在**，这个断层今天刚被看见。

【判断】这是当前设计最大的单点采纳障碍。修法方向（供主权者裁决，不替拍板）：给成员一个**装载面**——一个返回「岗位卡+名下任务判据+环路规程摘要」的只读动作，Lead spawn 时把一句「先调 mind_onboarding」写进 prompt 即可；或宿主侧在 childSessionMeta 落岗位（债㉑ 甲方案，不改宿主不闭环）。

## 十一、设计改进建议（分优先级，供主权者裁决）

**P0（设计层，值得尽快裁决）**

1. **给 §1 成败判据装上度量**——最小闭环：任务结账（settle）时记录「本任务引用了哪些既有记忆/能力 id」，月度即可回答「知识只涨不用吗」「同类问题成本降了吗」。不改这个，设计的 raison d'être 就永远是信仰问题。
2. **成员装载面**（§9.4）——一个返回岗位卡+名下判据+环路规程摘要的只读动作，或宿主侧 childSessionMeta 落岗位。采纳成本的钥匙。
3. **读面治理**——修 F1/F2 两条活 bug（用户可见的正确性问题）；workbench 给 LLM 的紧凑档与给人的完整档分离（117KB 无上限回传不可持续）。

**P1**

4. 设计文档回改机制：裁决落地同步回写《组织设计》并版本化（§7.4）。
5. 读面单源：记忆统计收敛为一个实现（status/workbench/query 三处口径合一，与 F2 同修）。

## 十二、结论

这套设计最了不起的地方，不是某个机制，而是**它对自己诚实的密度**：DESIGN-MAP 的「未接线」标注、设计债的「为什么现在不修」、裁决的修正记录、经历条目里成段的「我错了」——一个会自我纠错的治理系统，比一个完美的一次性设计值钱得多。

它当前最需要的东西也不是新机制，而是三件旧账：**量自己的收益、降别人的采纳成本、让设计文本跟上裁决**。加法做得够多了，该做减法和度量了。

最后一个如实标注：本报告自身未经独立复核，且评审者在评审过程中绕行了被评审系统的核心流程（§9.4）——按本组织自己的标准，这两条都应记为报告的置信折扣。若主权者要求，可按 2026-10-14 的复核闭环模式（提名→常任授权→spawn 复核员）对本报告做独立复核。
