## 三、四个实测真缺陷（三个已修，一个待裁决）

### 缺陷 1（**已修**）：物理删除不传播——晋升过的知识删不干净

**症状**：知识被 `promoteCrossProject` 晋升后，**同一个 id 同时住在两本账上**（本项目账 + 跨项目账，这是「双份留痕」的代价）。
`purge` 只抹掉 `entry.归属` 指向的那一本 ⇒ 另一本留下**全文副本且仍可被检索**，而审计记录写着「内容已抹掉」。

**复现读数**（临时夹具，修复前）：

```
② 已晋升岗位标签
   本项目账本条数： 1  跨项目账本条数： 1  同 id？ true
④ 物理删除后查询 p1：
       know-客户端版本低于-24-…｜状态=已失效｜内容=客户端版本低于 2.4 时需要兼容回退｜归属=p1
   删除后 本项目账本残留： 1  跨项目账本残留： 0
```

主权者以「这是敏感数据，必须清掉」为由删除，**内容仍然搜得到**。这正是评审稿 §C8 禁止的「原文禁读、副本仍可读」空窗。

**修法**：`purge` 扫遍「跨项目 + 该类全部项目账本」（`exists` 过滤），返回值与审计补「清理覆盖」字段（评审稿 §C8 要求记录覆盖范围）。

**验收（已做）**：

| 步骤 | 读数 |
|---|---|
| 原仓全量 | `preflight` 通过 · `node --test` **146/146 绿** |
| 新用例正跑 | `✔ 记忆：晋升过的知识被物理删除时，另一本账上的副本也必须抹掉` |
| **造坏校准**（临时副本里把扫描退回 `[entry.归属]`） | `✖ …` **fail 1** ⇒ 用例真的守得住；原仓零写入 |
| 改动面 | `src/memory.js` + `test/flow.test.js`，2 文件 54+/20− |

### 缺陷 2（**已裁决：方案 ①** → **已修**，提交 `aa8dbd0`）

**症状**：`invalidate` 追加 `invalid` 后，`query()` 的**命中**里仍然返回该条（只被排除 `物理删除`）。
读数：失效后带原项目检索 `命中：1`。检索面每条都带 `状态`，所以调用方**理论上**能自己判断——
但默认返回「已失效」的条目，等于把「下一次召回不再把旧结论当当前事实」（补充建议 §下一步 第 4 条）交给调用方自觉。

评审稿 §A9 的方案 B 正是针对此：**由确定规则生成当前有效视图**。设计稿 v1.5 §7 只写了「追加 invalid 状态」，**没有**规定召回是否排除。

**所以这是设计选择，不是实现 bug，我没有单方面改**——交主权者裁决。三个选项与裁决：

| 选项 | 做法 | 代价 |
|---|---|---|
| **① 已采纳** | `query` 默认排除 `已失效/被推翻`（`条目` 仍全量可见，供追溯） | 需明确「历史查询」怎么开 ⇒ 已定为 **`含失效: true`**（新增工具参数） |
| ② | 加 `模式: current/historical`（照评审稿 D3） | 更清楚，但接口面变大 |
| ③ | 保持现状，靠调用方读 `状态` | 零改动，但「旧结论继续冒充当前事实」的门一直开着 |

**修法**：默认只对「当前有效视图」建索引；`已降权` **不在排除之列**（降权＝冷，不是错）。
判据做成**粘性**：只要追加过 `invalid` / `推翻` 就不再进当前召回，之后的降权不许复活它——
因为 `fold` 是按**秒级** `追于` 覆盖的，同秒「先失效、后降权」会把最终状态变成 `已降权`，只看最后一个状态就会漏。
没进召回的条数进 `口径`，并在 `说明` 里给出拉回它的办法（不许折成「没找到」）。

**顺带修一句假读数**：`口径.排除失效` 原本在 `含失效: true` 时也报非零（一条都没排除却报成排除了）；
改为只报实际排除数，「一共有几条失效」另用 `失效条目数` 报，并加断言钉住。

### 缺陷 3（**已裁决：方案 ①** → **已修**，提交 `aa8dbd0`）

**这是重启后做活体验收时抓到的，修完缺陷 1 才暴露出来。**

`objectId()` 把 seed 折成最多 **40 字符**放进 id（`src/kernel/ids.js:53`），而 `memory.remember` 传的 seed 是
**正文前 40 字**（`src/memory.js`：`objectId(kind, \`${text.slice(0, 40)}/${subject.id}\`)`）。
这个 id 又进**每一条**审计记录的 `对象.id`——而审计是**只增、连主权者也只能追加更正**的。

**活体读数**（一次性的验收标记走完 写入 → 晋升 → purge 之后，审计原文）：

```
--- 状态变更 ---
对象.id = know-验收标记-zz7k客户端版本低于-24-时需要兼容回退-lead-e2bf35
详情 = {"类":"知识","来源":"Lead 的活体验收：…"}
--- 不可逆操作 ---
对象.id = know-验收标记-zz7k客户端版本低于-24-时需要兼容回退-lead-e2bf35
详情 = {"理由":"这是敏感数据，必须清掉（活体验收收尾）","类":"知识","清理覆盖":[…]}
```

记忆账本已 **0 残留**（缺陷 1 的修复**确实有效**，见 §五），但**正文前 40 字仍永久可读地留在审计链里**。
于是 `purge` 的审计写着「内容已抹掉」，同一份日志里却留着内容——**第二次自相矛盾**。

**违反**：评审稿 §A5 / §C8 明写删除凭据应是「**随机对象 ID**……**不保留被删原文或可枚举的敏感标题**」；
评审稿 §C2 也写「使用不含秘密、不可推导客户身份的**短前缀加随机标识**」——实现用的是**内容派生的 slug**，不是随机标识。

**顺带一处文档与实现不符**：`ids.js` 开头注释说「id 由 kind + 主体 + 序号推导，索引丢了也能从目录名重建」，
但实现把 **seed（正文）与 `at`（时间戳）** 都喂进了哈希 ⇒ 这个 id **不可能**从 kind + 主体 + 序号推导出来。

**不可逆性**：已经写进审计的 id **撤不回来**（只增是设计红线）。所以这条只能「往前修」，不能「修回去」。

| 选项 | 做法 | 取舍 |
|---|---|---|
| **① 已采纳** | 记忆 id 的 seed 不再用正文：改用 `类/主体/时刻` 之类的非内容种子；标题另存 `标题` 字段供人读 | 种子一行改动、不动 id 方案、不动文件名（记忆是 JSONL，无 per-id 文件）；代价是新 id 不再自带标题 |
| ② | 照评审稿 §C2 改**随机标识** | 最干净，但 id 方案整体变更，波及全部 8 类对象与既有引用 |
| ③ | 审计的 `对象.id` 存不可读引用，另表映射到可读 id | 审计不再泄漏，但多一层映射要维护，且旧审计里的 id 已经在 |
| ④ | 接受现状，把「敏感内容不许进正文」变成纪律 | 零改动，但等于放弃 purge 对敏感数据的承诺 |

**修法**：`remember` 的 id 种子改为 `类/主体`，并配一个**严格递增时刻** `#nextStamp()`——
种子去掉正文后，同毫秒、同主体的两条会算出同一个 id，而 `fold()` 是按 id 归并的，
撞 id 会让两条记忆**静默合成一条**（不报错，最难发现的那种）。人可读的标题移进 `标题` 字段：
它在账本里，`purge` 能连带抹掉；而 id 里的东西抹不掉。

**新 id 形状**：`know-知识-lead-024045`（旧形状是 `know-验收标记-zz7k客户端版本低于-24-…`）。

### 缺陷 4（**新发现，待裁决**）：记忆之间没有血缘 ⇒ 删除覆盖不到「引用过该内容」的其它条目

查 `src/`：**没有** `derived_from` / `source_refs` / 血缘 / 派生 任何一个（grep 零命中）。
记忆条目的字段只有 `id / 类 / 标题 / 内容 / 来源{谁,怎么知道} / 归属 / 项目 / 岗位 / 标签 / 状态 / 记于 / 轮`——
`来源` 是一句**自由文本**，不是可遍历的引用。

评审稿 §C2 要求 `source_refs` / `derived_from` / `verification_refs`；§C8 更要求
「源对象进入 pending_delete 时，同步阻止依赖它的派生摘要、记忆与待发布产物进入读取、注入与输出」。
**没有血缘，这条要求在实现上不可能满足。**
**本会话就撞上了一个实例**：验收标记 `ZZ7K` 被 purge 之后，`跨项目\经历.jsonl` 里**仍然搜得到 `ZZ7K`**——
因为我的缺陷报告**在正文里引用了这个标记**。那不是「删漏了」，而是「另一条合法记忆引用了它」，
系统无从知道两者有关系。标记本身不是敏感数据，所以实际危害为零；但换成真敏感内容，
`purge` 的覆盖范围就**只能保证「被删的那条自己」**，保证不了任何引用过它的条目。

| 选项 | 做法 | 取舍 |
|---|---|---|
| **① 推荐** | 记忆加 `引用` 字段（存 id 数组），purge 时按它**反向查找**并保守隔离引用方 | 不引入完整血缘图，能覆盖「显式引用」这一大类；代价是只对显式引用有效 |
| ② | 照评审稿 §C2/§C8 上完整血缘（`source_refs` + `derived_from` + 邻接索引） | 最彻底，但等于把评审稿 §C 的数据模型整套搬进来，是「记忆真源分层」那一档的工程量 |
| ③ | 不改，把「别在自己的记忆里引用敏感内容」变成纪律 | 零改动，但 purge 的承诺范围必须**如实缩小**到「只覆盖被删那条自身」 |

**同一族的第三处残留**（已实测，未改）：`purge` 只删**内容行**，**不删指向该 id 的状态行**——
状态行有自己的 id（`ledger-…`），所以按 id 过滤时它留下，成为一条悬空记录。实测 purge 后账本里剩的那一行就是它：

```json
{"id":"ledger-know-知识-lead-024045invalid-5c6944","指向":"know-知识-lead-024045",
 "追加":"invalid","追于":"2026-10-08T13:53:07Z",
 "依据":"活体验收：把这条判成失效，看它是否退出默认召回","主体":{…}}
```

它**不含正文**（id 去掉正文之后 `指向` 也已经是不可读的短 id），而且「谁在什么时候以什么依据处置过」正是设计要保留的留痕
（§C8 说审计保留「授权依据」）。所以**保留它是对的**；要留意的是 `依据` 是**调用方自由文本**——
真敏感内容别写进 `依据` 里。这一条不改，只记在这里。
