> 日期：2026-10-08（Asia/Singapore）  
> 依据：同目录《组织设计.md》，心智·数字组织设计 v1.5，2026-10-07。  
> 状态：**评审与实施建议稿，供原作者裁决；不代表原设计已采纳，也不代表系统已实现或测试通过。**  
> 交付范围：前一轮架构评审的完整决策覆盖，以及新增的记忆写入、存储、有效态、召回、上下文注入、删除恢复与评测方案。  
> 部署假设：单用户、本地部署、少量成员并发、成本敏感；第一版不使用数据库，不引入向量检索服务。规模、技术栈和机器性能未提供，性能参数均为待验证初值。  
> 原设计文件保持不变。本文中的文件树、接口和数据样例是拟议规格，尚未创建对应运行系统。

## 阅读顺序

1. **第一部分**保留现有架构审核：13 组建议，每组有方案比较、推荐理由和验收例。
2. **第二部分**给出记忆方案及关键取舍：用于决定做什么、为什么这样做。
3. **第三部分**给出数据与存储协议：用于后续实现存储、状态恢复和删除。
4. **第四部分**给出召回与注入流程：用于实现查询、排序、证据包和上下文装配。
5. **第五部分**给出贯穿案例、验收矩阵和实施顺序。
6. **第六部分**列出需要同步修改原稿的条款，以及仍需实测确定的参数。

## 结论与推荐组合

组织骨架可以保留。当前需要补齐的核心，是各组件之间可验证的行为契约，以及记忆如何形成、更新并被正确使用。原稿不能再仅以“剩实施顺序”概括未决问题；原稿 §13 #7 也仍保留显式跨项目检索的待定项。

本文推荐组合是：

**不可变 Markdown 修订正文 + 追加业务提交记录 + 可重建的有效记忆视图和本地词面索引 + 授权范围内的多路召回 + 确定性融合 + 带来源的有限证据包。**

记忆服务提供候选证据；任务执行器内的上下文装配器决定本次注入哪些证据，策略引擎约束其范围。能力库仍独立保存“怎么做”的规程。所有记忆内容均作为资料读取，不能通过检索结果改变权限、规则或工具授权。

这里的“无数据库”保留了文件作为持久载体，同时也意味着团队需要承担提交、恢复、索引更新和删除传播的工程工作。它是一项有成本的部署选择。

# 第一部分：原架构评审

## A0. 评审口径

P0：开放相关自主能力前必须明确。P1：试运行应补齐。P2：用实测决定优化。风险场景由原文推导，不表示已经发现实现中的实际漏洞。

值得保留：岗位持久、实例临时；工作台仅做投影；能力单源引用；未验不等于通过；Lead 不能改复核结论；暂不增加协调层；检索变化必须跑回归集。

## A1. P0：真实权限边界与任务内授权

**依据：**原稿 §2、§6、§7.5、§9。

目录与标签不能单独保证隔离。如果成员持有宿主完整 shell 权限，就可能直接读其他项目、改角色卡或审计文件。现有判定接口还需明确任务、项目、段级目标、对象版本及撤权状态如何从可信记录取得。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| **A，推荐** | 统一工具入口持有真实权限；成员提交结构化请求；通用命令进入受限环境 | 与本地少并发最匹配，能让授权对应实际执行 |
| B | 每个实例独立系统账号或容器 | 隔离强；环境和生命周期管理较重，运行第三方代码时再优先考虑 |
| C | 模型只生成计划，所有副作用由人执行 | 适合早期验证，但不适合长期自治 |

有效权限为岗位权限、任务范围、项目范围、工具总范围的交集，并受拒绝名单约束。主体身份、对象标签不可由调用者自行宣称；产生副作用前重新检查撤权。策略引擎启动加载规则、读取授权事实和写拒绝日志的受信任内部通道也必须写清，避免自举与递归依赖。

**验收例：**排队后撤权的动作无法执行；成员无法通过 shell 直接读取其他项目或改日志。策略判定与执行控制是两个职责，可以在同一程序内完成，参见 [OPA 官方说明](https://www.openpolicyagent.org/docs)。

## A2. P0：唯一事实源、提交与恢复

**依据：**原稿 §6、§8、§9、§12、§14。

§8 将注册表称为权限事实源，§14 又称其为索引，需要统一。推荐把角色卡、身份档案、实例绑定与撤权记录视为持久事实，注册表作为唯一查询入口和可重建索引。索引失配时不能继续使用旧授权。

正文、任务、旧版与审计分别落盘，一次变更何时成功仍未定义。先写状态会留下无账变更，先记成功会留下假成功，自动保留旧版不足以处理这些中间态。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| **A，推荐** | 文件系统、单写入者、唯一操作号、业务提交记录、恢复协议 | 保留原部署边界；需要认真实现和验证崩溃恢复 |
| B | SQLite 管事务状态，正文保留文件 | 减少自研事务工作，但需要改变“不上数据库”的当前约束 |
| C | 全部业务状态由事件流重建 | 重放统一，但全系统事件化、迁移和投影成本更高 |

业务提交记录是底座恢复设施；审计仍负责事实留痕，不承担业务状态。外部发布成功但回执丢失时，进入“结果未知”，先查询或裁定，不能当普通失败重试。文件多处写入的一致性原理可参考 [SQLite 原子提交文档](https://www.sqlite.org/atomiccommit.html)，本文并未因此指定使用 SQLite。

**验收例：**在各写入阶段强制退出，恢复后没有假成功、无账可见变更或重复外部动作。

## A3. P0：安全更新的合格回滚集合

**依据：**原稿 §4、§5。

“探针全绿的最近一版”可能是已知漏洞版本，也可能不兼容新数据。探针长期全绿通常可以正常，健康检查应验证实际执行、已知正反例和结果时效。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| **A，推荐** | 限定强更范围，验证来源、兼容性与探针，只回滚到合格集合 | 同时保留自动更新和可解释的失败行为 |
| B | 安全更新全部人工批准 | 权责清楚，但失联期间无法持续强更 |
| C | 厂家作为最终信任根，签名、通知、留痕 | 最易落地；不修改红线的保证主要依赖对厂家的信任 |

合格目标同时满足：探针通过、未被安全撤销、数据兼容。没有目标时停用受影响能力并告警。普通补丁不能自行替换监督它的更新验证、探针声明与恢复入口。签名和版本防护可参考 [TUF 规范](https://theupdateframework.github.io/specification/v1.0.36/)；签名不证明更新行为正确。

**验收例：**新版失败、旧版有漏洞时，进入受限状态，不能在两个坏版本间循环。

## A4. P0：跨项目知识的披露授权

**依据：**原稿 §7、§7.5。

“可复用”不能直接推出“整条可共享”。项目记录里的客户名称、路径、参数可能随岗位标签进入另一个项目。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| **A，推荐** | 提炼通用知识，经披露检查后发布到岗位知识；来源引用仍受权限限制 | 保留复用价值，边界直观 |
| B | 同一对象做段级安全投影 | 正文重复少，但授权、引用展开和更新继承复杂 |
| C | 项目知识永不提升，岗位知识单独整理 | 隔离最简单，经验复用较慢 |

包含项目细节的记录生成经过处理的新对象；已完全通用的原记录也必须经过独立范围授权。引用不授予来源访问权。记忆中的外部指令始终作为数据处理。

**验收例：**晋升含虚构客户名和路径的经验后，其他项目只能读取通用结论。

## A5. P0：不可变审计与敏感删除

**依据：**原稿 §3、§6、§7。

失败原文可能包含令牌。若错误输出、历史版本和备份全部永久保留，删除当前文件不能满足删除意图。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| A | 所有原始输入输出永久追加 | 排障方便，但敏感副本最多、删除困难 |
| **B，推荐** | 审计保留必要事件元数据；详情正文单独受控保存；入账前脱敏 | 兼顾追责与删除能力 |
| C | 独立归档系统与不可改存储 | 适合强外部审计要求，本地首版维护成本偏高 |

“失败全记”应落实为失败类别、操作号、原因摘要及受控详情引用。删除覆盖正文、旧版、索引、备份与派生知识处理规则。审计只增的威胁模型也要明确：防止普通代理篡改，与阻止本机管理员物理修改，是不同保证。

**验收例：**敏感错误输出不进入永久日志；授权删除后的内容不能通过历史检索复现。

## A6. P1：稳定身份与可修改职责分开

**依据：**原稿 §2、§4、§5。

复核者身份、权限和判据归用户修改，与身份核心锁定、随产品更新存在潜在冲突，取决于“身份核心”的具体范围。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| **A，推荐** | 稳定身份 ID 与职责、权限、判据分离，分别版本化和授权 | 身份连续性与演进同时成立 |
| B | 出厂角色不可改，只能派生本机角色 | 边界清楚，但增加继承、迁移和双身份引用 |
| C | 所有本机角色归用户，厂家只提建议 | 易理解，但普通模板更新也可能频繁打扰用户 |

模型代次、能力版本、职责版本单独记录。复核者关键字段的特殊授权优先于一般模板更新。

**验收例：**产品更新不能改掉本机复核者权限；岗位职责改变不丢履历。

## A7. P1：复核绑定具体输入与版本

**依据：**原稿 §2、§8、§14.4。

独立角色不足以单独保证复核独立：被验方不能在过程中改变本次复核的规程与材料。只引用产物 ID，也不能证明后来修改的版本已经验过。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| **A，推荐** | 固定产物、判据、能力与证据版本；结论绑定版本 | 对现有架构改动小，容易验证 |
| B | 独立服务或维护者负责复核 | 隔离强，但维护成本高，仍需防共同知识错误 |
| C | 重要结果都由用户验收 | 适合高风险任务，全量采用会成为瓶颈 |

提案者不能自批；Lead 自己被验时也受被验方限制。复核者可追加结论，不能改被验对象。执行证据用 id@version；当前撤权、删除和安全禁止仍优先，冻结旧版本不能获得永久读权。

**验收例：**验收后修改产物，原结论不得为新版放行。

## A8. P1：任务状态机、判据修订与失联动作表

**依据：**原稿 §4、§7—§10。

需明确未验、补证、超时、撤回、成员退出、旧消息迟到和执行中重启。“所有自治冻结、记忆照常”应区分业务证据记录与治理变更。冻结的判据还可能一开始就漏掉用户要求。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| **A，推荐** | 小状态机，分开任务、执行轮次、等待原因，另列失联动作表 | 能覆盖当前主干，复杂度可控 |
| B | 审批、补证、重试全部建子任务 | 复杂依赖清晰，但节点容易膨胀 |
| C | 通用工作流引擎 | 流程种类多时有价值，当前引入偏早 |

判据映射回用户要求；发现漏项要产生有理由的修订。打回计数归稳定任务，补证有次数或时间预算。消息带轮次、去重键；会审名单冻结，旧交卷不能解锁新会审。失联期间允许已授权业务和证据记录，冻结扩权、规则修改和共享能力生效；恢复交互不等于批准待决项。

**验收例：**离线、重启与迟到消息同时发生，任务落在确定等待状态，不无限重试、不自动通过。

## A9. P1：追加历史与当前有效记忆分开

**依据：**原稿 §7、§11。

旧正文可能比新增 invalid 状态更匹配查询，导致失效知识继续排第一。多次复述也不能变成独立证据。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| A | 每次由模型理解全部原始历史 | 开发简单，历史越长成本越高且解释不稳定 |
| **B，推荐** | 原记录追加保存，确定规则生成当前有效视图 | 保留历史，读取稳定 |
| C | 当前正文覆盖，另存历史 | 易读，但需调整追加原则和历史语义 |

更正、失效、替代必须指向对象；未决冲突并列。区分用户陈述、观察、模型推断和已验证结论。身份携带知识检索范围，具体正文按任务与预算装配。

**验收例：**新增、更正、失效后默认检索结果稳定；历史模式可查全过程。

## A10. P1：自治能力优先须经过准入

**依据：**原稿 §5、§7。

工具升级后，旧自治规程可能因来源优先而压过已经修复的出厂规程。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| A | 自治固定优先 | 简单，但来源不能证明兼容性 |
| **B，推荐** | 先筛验证状态、环境和依赖，再执行自治优先 | 保留本地适配价值并控制传播 |
| C | 每次 Lead 比较两版 | 适合偶发冲突，常态调用成本高 |

能力保存前置条件、验证用例、依赖版本和状态。新经验先是候选，依赖变化可重新待验；真实 ID 区分两个库，运行时记录版本。

**验收例：**不兼容规程不能靠“本地优先”自动胜出。

## A11. P1：独立证据、反趋同与反讨好

**依据：**原稿 §1、§10、§12。

独立盲答仍可能共同依赖一条错误知识；正确的确定性任务也可能全票一致。强制反对容易产生无价值分歧。迎合用户与成员趋同要分别评测，相关现象可参考 [Anthropic 原始研究](https://www.anthropic.com/research/towards-understanding-sycophancy-in-language-models)。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| A | 固定多人盲答、强制反对、一致抽检 | 好执行，但可能增加表面分歧 |
| **B，推荐** | 盲答与独立验证并用；查证、找反例，允许未发现反例 | 围绕真实错误，成本可控 |
| C | 长期多模型多供应商会审 | 可能增加差异，成本和数据边界更复杂 |

风险、共同单一来源、无法复现与证据冲突触发进一步复核。Lead 汇总保留实质少数证据及处置理由。多代理收益需有本地基线，不能从代理数量直接推出；[Debate or Vote](https://arxiv.org/abs/2508.17536)的实验也说明讨论与投票的贡献应分开比较。

**验收例：**事实不变，用户分别表态支持相反结论与保持中立，测无新证据改口率；另测真实发现率和无效反对率。

## A12. P2：检索分成过滤、召回与排序

**依据：**原稿 §11。

BM25 已有文档长度归一化，额外再除以长度需证明价值，参见 [《信息检索导论》BM25](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html)。中文分词、同义词、精确标识符、有效态和作用域更值得先补。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| A | 基础 BM25 调参 | 适合基线，不解决授权与同义改写 |
| **B，推荐** | 先过滤权限与状态，结合分词、精确匹配、别名，再进行词面排序 | 成本可控、可定位失败原因 |
| C | 向量与词面混合检索 | 可能改善语义召回，但当前尚无收益证据，且有原稿重开条件 |

分别判断答案不在候选、排位过低、进入上下文却未被正确使用。满足原稿重开条件后再比较混合检索。

**验收例：**回归覆盖同义改写、代码路径、长短文、失效记录、同词不同项目与正确零命中。

## A13. P1：按任务价值启用组织成本

**依据：**原稿 §1、§8、§13。

长期记忆和隔离可以由一个执行器加外部存储实现，不能单凭这两项推出所有任务必须多人会审。成本下降也可能来自任务变化或模型价格变化。

| 方案 | 做法 | 选择理由 |
|---|---|---|
| A | 单执行器、外部记忆、工具验证 | 最好做对照基线，复杂任务缺少独立复核 |
| **B，推荐** | 八件保持逻辑职责，按风险和难度选择短流程或完整流程 | 质量与成本可比较 |
| C | 所有任务都完整会审与复核 | 适合高价值任务，简单工作固定开销大 |

同一批任务、相同模型配置与明确预算，报告质量、返工、人工分钟、调用费用、耗时和重复犯错率。核心是每个成功任务的总成本，同时列质量指标。先证明收益，再增加层级或常态多代理。

**验收例：**在真实任务集比较三种配置，不能只报 token 下降或记忆数量增加。

# 第二部分：记忆方案的架构与取舍

## B1. 保留的约束与本方案新增的决定

保留双区、项目隔离、能力库独立、岗位持久、记忆追加、默认词面检索、不迁移旧数据。第一版仍不使用数据库；索引是可删除重建的文件和内存结构。

新增决定包括：记忆正文如何存、状态如何生效、写入如何提交、索引如何追上变化、召回如何过滤与排序、上下文由谁装配。这些均是本方案的推荐，不能直接视为原作者已批准的法律或产品要求。

| 问题 | 本文选择 | 原稿兼容性 |
|---|---|---|
| 记忆真源 | 不可变修订正文 + 已提交业务事件 | 细化追加原则 |
| 当前有效内容 | 由真源确定性重建的视图 | 新增读取契约 |
| 正文位置 | 所有修订，包括第一版，统一放版本历史 | 对原“当前对象 + 改前备份”的记忆专用调整，避免两份权威正文 |
| 状态与权限 | 当前状态、证据质量、可见范围分别记录 | 拆开原来容易混用的标签含义 |
| 记忆类 | 知识、经历、偏好、作答；能力另库 | 保留原边界 |
| 召回 | 精确匹配 + 中文词面 BM25 + 按需字二元组 | 无向量，符合原部署决策 |
| 注入者 | 任务执行器中的上下文装配器 | 记忆服务仍不决定注入，不增加第九件组织基础设施 |
| 跨项目 | 默认只读当前项目和已发布岗位知识 | 原项目显式跨项目读取默认关闭，受限授权单独处理 |
| 失联 | 业务证据可记，共享晋升与治理改变暂停 | 明确“记忆照常”的范围 |
| 上线标准 | 先过权限、删除、恢复门槛，再比较质量与成本 | 将原则变为可验收契约 |

## B2. 存储方案比较

| 方案 | 具体组成 | 优点 | 为什么选或暂不选 |
|---|---|---|---|
| S1 | 普通 Markdown + 文件扫描，状态交给调用模型解释 | 开发最少，人能直接看 | 可做最初对照；有效态、并发和恢复容易不稳定，不作正式默认 |
| **S2，推荐** | 不可变 Markdown 修订 + 追加提交记录 + 可重建有效视图/倒排索引 | 保留本地与无数据库约束，能明确单源和读取语义 | 首版采用；代价是自研并验证小型提交、恢复与索引协议 |
| S3 | SQLite 事务状态/全文索引 + 文件正文 | 有成熟事务与索引能力 | 约束放宽时是务实替代；当前不静默违背“不上数据库” |
| S4 | 文件/数据库正文 + 向量索引或图检索服务 | 适合经实测确认的语义或复杂关系检索瓶颈 | 增加同步、删除、权限过滤与维护成本；当前没有必要性证据 |

S2 的适用边界是本机单写入者、允许后台重建、数据量可由本地索引管理。未来若多个宿主并发写、恢复或索引维护成本明显上升，应重新比较 S3，避免无期限手写数据库功能。SQLite 的全文能力可参考 [FTS5 官方文档](https://www.sqlite.org/fts5.html)；这里不指定最终语言和检索库。

## B3. 各类信息的职责、默认检索面与晋升

| 信息 | 内容与归属 | 默认检索 | 写入与有效性 |
|---|---|---|---|
| 项目知识 | 当前决定、约束、已验证事实、待验证断言；来源项目必填 | 当前项目中允许读取且生效的知识 | 候选可保存；未验证推断不能直接变成已确认事实 |
| 岗位知识 | 经过共享裁决的通用规律，带适用条件 | 当前岗位有权使用的已发布集合 | 项目提炼、披露检查、独立复核后生效；保留受控血缘 |
| 经历 | 发生了什么、证据、结果、失败原因和纠正动作 | 当前项目相关的结构化经历 | 追加事实；“当时记录过”不代表当时判断正确 |
| 部署偏好 | 用户明确的表达、工作方式等偏好 | 当前任务相关且允许读取的键 | 显式陈述可按既有授权生效；推断偏好保持候选；当前用户要求优先 |
| 作答 | 已提交回答、分歧与复核产物引用 | 默认排除；显式追溯且有权时读取 | 已提交版本只增；不能当成独立事实来源；不要求存模型隐藏思维过程 |
| 能力 | 步骤、前置条件、工具契约和验证用例 | 由能力库单独解析 | 候选规程另走能力准入与兼容检查 |
| 宪章/法律/权限 | 当前受控规则 | 独立受控加载，不能依赖相关性检索 | 单独授权和版本，不接受记忆正文宣称的授权 |
| 审计/原始工具详情 | 安全与运行事实 | 普通记忆查询默认排除 | 专门审计入口；失败摘要可形成经历，敏感原文不复制 |

组织经历可以在逻辑上统一成账本，物理与访问范围仍按项目划分。组织级“履历”只保存必要的非敏感摘要，不能通过全局履历绕开项目隔离。

第一版拒绝把凭据、令牌等秘密写入普通记忆；确需使用时保存受控秘密对象的引用，由工具代理按授权取用。格式校验和简单秘密检测不能保证识别所有敏感内容，仍依赖范围、最小保存和删除机制。

## B4. 写入、颗粒度与质量取舍

| 决策 | A | **B，推荐** | C |
|---|---|---|---|
| 保存粒度 | 整个会话一条：便宜，但检索噪声和权限边界粗 | 一条可独立更正的断言或一段完整事件；原始材料另存引用 | 每句一个碎片：精细，但容易丢限定条件与关联 |
| 写入时机 | 每轮自动大量提取：记得多，但噪声与费用高 | 显式记住、重要决定、失败纠正、阶段完成时触发 | 只在任务结束写：省事，但中断可能失去进展 |
| 可信程度 | 只存原文与来源：最简单，判断全部交给调用方 | 明确证据类别与验证记录，和生命周期分开 | 连续概率评分：需校准数据，否则精确数字没有依据 |
| 自动整理 | 模型抽取后直接生效：快，但容易固化幻觉 | 模型提出候选，结构校验与对应授权/证据规则决定激活 | 每条人工批准：稳妥但负担大 |
| 冷记忆 | 定期物理删：省空间但可能丢重要历史 | 降权、归档和重建索引，不因少用就判错 | 永远同权搜索：实现简单，噪声随时间增长 |

推荐的一条知识包含一个主断言及必要条件；例如“客户端版本低于 2.4 时启用兼容回退”，不能将“低于 2.4”切出该断言。长来源按语义段落分块，块继承对象权限、版本和状态；不允许同一块跨越不同授权段。

## B5. 组件流转与单源

```text
用户/工具结果/成员产物
          │
          ▼
可信身份与任务绑定 → 策略判定 → 结构/来源/敏感性检查
          │
          ▼
候选或更正请求 → 单写入者 → 不可变正文 + 业务提交记录
                                     │             │
                                     │             └→ 审计事实与回执
                                     ▼
                           当前有效视图 + 本地索引
                                     │
任务请求 → 当前权限与作用域 → 多路召回 → 有限证据包
                                     │
                                     ▼
任务执行器中的上下文装配器 → 再查当前权限/失效 → 回答或执行
                                     │
                                     └→ 使用反馈；事实更正另走写入流程
```

索引和目录可以丢失重建；正文与提交历史不能靠索引反推。只追加约束权威正文与变化历史，派生视图、索引与缓存可以覆盖、清理和重建。记忆里的“某用户同意了”是一个断言，真实授权仍须在可信授权记录中存在。独立复核者资料独立授权；Lead 正在被验时不能借全局身份读取它。

# 第三部分：数据模型、写入与存储协议

## C1. 拟议目录

```text
mind/
└── 集体L2-共享基础设施/
    └── 记忆服务/                     程序、schema、默认分词与召回配置

mind-private/

│   │   ├── 跨项目/

│   │   ├── <project-id>/

│   │   │   ├── 经历/                 目录与索引

│   │   ├── 复核者私有/<role-id>/      独立命名空间与访问规则
│   │   ├── _视图/<generation>/        有效态、血缘、冲突组、进度
│   │   ├── _索引/<generation>/        分区倒排索引、精确词、词典版本

│       ├── 000001.md                 含第一版；正文一经提交不覆盖

│   ├── journal-YYYY-MM.jsonl          有序业务提交与恢复记录
│   ├── staged/<operation-id>/        尚未提交的材料
│   └── checkpoints/                  有校验和的重放加速点，可重建
├── _删除登记/                        受保护、最小化的删除控制记录
```

各分类目录可生成可重建的“目录.md”，链接到当前明确修订，不再复制一份可编辑正文。目录名只是定位约定，实际读写仍由可信对象标签和执行环境控制。

**单源裁定：**正文事实来自不可变修订；生命周期、可见范围、当前头指针等来自已提交事件。原始正文中写入时的标签不能盖过后续撤权或失效事件。全局版本目录只对受控存储组件开放，不能因为所有正文都在该目录就让成员全量读取。

## C2. 标识、类型与状态分开

稳定 ID 在整个部署内唯一，使用不含秘密、不可推导客户身份的短前缀加随机标识；同名不代表同 ID。系统拒绝碰撞和重复创建。正文修订递增，记录引用固定为 id@revision；回滚不覆盖旧记录，只创建有来源的新修订或新的状态变更。

建议对原数据模型做以下明确扩展：

| 字段组 | 内容 | 语义 |
|---|---|---|
| 对象身份 | id、revision、schema_version、kind=记忆、memory_type | kind 新增“记忆”，memory_type 为知识/经历/偏好/作答 |
| 治理属性 | authority、mutation_policy、zone、domain | authority 表示谁有权改；append_only 是修改方式，不是与法律平级的权力档 |
| 来源与范围 | origin_project、namespace、role_ids、created_by、task_id | 来源项目与允许读取范围分开；角色字段不自行授予跨项目访问 |
| 内容语义 | title、claim_key、entities、keywords、body | claim_key 辅助识别同一断言，不是自动判定冲突的真理规则 |
| 时间 | recorded_at、valid_from、valid_to | 写入时间与事实适用时间分开；未知适用时间保持未知 |
| 溯源 | source_refs、derived_from、verification_refs | 都指向明确版本；访问引用还需独立授权 |
| 当前状态，来自事件 | lifecycle、evidence_state、visibility、head_revision、conflict_group、state_seq | 读取当前视图，不能只读旧正文元数据 |

对象生命周期采用 candidate、active、invalid、archived、pending_delete、deleted，并保存 head_revision。每个修订另有 candidate、adopted、superseded、invalid 状态及各自的证据状态。证据状态采用 unverified、supported、disputed，并保存依据，不将相关度分数当成事实成立概率。超过 valid_to 的条目在当前查询中视为不适用，不必覆盖旧正文。

已有有效第 1 版时，新增候选第 2 版不会自动改变 head_revision，也不会把整个对象改成候选。只有显式采纳事件才切换当前修订。失效必须声明作用于整个对象或某个修订；当前修订失效后不自动回退旧版，全对象失效也不能通过添加新正文隐式解除。恢复有效需显式 revalidate 事件与对应依据。

active 表示进入允许的读取流程，仍须附证据状态；默认回答不把 active/unverified 当成确定事实。第一版自动候选均不进入常规答案证据面，显式调查模式可读取并标注候选。

## C3. 单条知识的拟议格式

每个修订保存 UTF-8 Markdown，开头使用严格 schema 的 YAML 元数据。正文模板按类型校验；重复键、未知枚举、不合法引用和缺失来源拒写。普通成员只通过写接口提交内容，不能直接改元数据文件。

以下为虚构样例，ID 与内容不代表当前部署事实：

```yaml
---
schema_version: 1
id: mem-a7c2f8d1
revision: 1
kind: 记忆
memory_type: 知识
authority: 自治
mutation_policy: append_only
zone: 私有
domain: 集体
origin_project: project-a
namespace_at_creation: project:project-a
role_ids_at_creation: []
created_by: instance-worker-17
task_id: task-118
recorded_at: '2026-10-08T10:00:00+08:00'
valid_from: '2026-10-08T09:30:00+08:00'
valid_to: null
title: 旧客户端需要兼容回退
claim_key: cache.compatibility.fallback
epistemic_type: tool_observation
entities: [cache-service, client]
keywords: [兼容回退, 客户端版本]
source_refs:
  - id: artifact-test-118
    revision: 1
    locator: compatibility-cases
derived_from: []
---
```

```markdown
## 结论
客户端版本低于 2.4 时需要兼容回退。

## 适用条件
仅适用于 task-118 测试覆盖的客户端与服务端组合。

## 证据
artifact-test-118@1 中的兼容性测试结果。

## 限制与待验证项
未验证其他客户端实现；不能外推为所有版本都需要回退。
```

完整性摘要由写入器计算并写入提交记录，正文不包含对自身整个文件的循环摘要。当前激活、撤销、冲突等状态由后续事件决定，不在这份不可变正文里反复改写。

经历模板包含“触发—观察—操作—结果—原因证据—纠正—可复用条件”。偏好模板包含“偏好键—用户原意—适用范围—是否显式陈述—时间”。作答模板包含“任务/轮次—交卷内容或产物引用—证据引用—实际分歧—最终处置”；不保存无必要的原始工具洪流。

## C4. 状态事件与冲突裁决

状态变化必须明确目标、预期前态、操作者、授权依据、操作号与证据。例子是一个失效操作的逻辑请求；身份和权限由网关核验，不信任调用者自报：

```json
{
  "operation_id": "op-9bc143ef",
  "action": "invalidate",
  "scope": "revision",
  "target": {"id": "mem-a7c2f8d1", "revision": 1},
  "expected_state_seq": 120,
  "reason_code": "contradicted_by_test",
  "evidence_refs": [{"id": "artifact-test-126", "revision": 1}],
  "replacement_ref": null
}
```

常用事件为创建修订、激活、替代、失效、标记争议、解决争议、降权、归档、申请删除与完成清理。单写入者分配严格递增提交序号；预期前态不符时返回冲突，不静默覆盖。时间戳用于解释时间，不作为并发裁决的唯一依据。

| 变化 | 处理规则 |
|---|---|
| 新事实 | 创建候选；来源与验证规则满足后激活 |
| 明确用户偏好 | 可信交互记录支持，按既有偏好授权写入；不等于工具权限授权 |
| 模型推断 | 标注 unverified，默认候选；被反复引用也不自动升级 |
| 事实随时间变化 | 保存新适用区间；旧事实可继续回答过去的问题 |
| 更正过去错误 | 明确 supersedes/invalidates 关系；保留原错误和何时得知错误 |
| 相互矛盾且未裁决 | 标 disputed，关联冲突组；不以最后写入者胜出 |
| 单次使用失败 | 保存失败证据，检查适用条件；不自动推翻整条通用知识 |
| 低频或长期未用 | 降权或归档，不视为错误，不自动物理删除 |

记忆写入权限不等于裁决权限。成员可按任务范围记录证据、提出候选；Lead 可整理并提交变更，组织级晋升仍需遵守提案者不得自批。机器可验证且预先授权的低风险激活可由确定规则执行；没有对应规则时保持候选或待决，不一概要求用户逐条确认。失联期间仅沿用既有的项目内激活规则，不得修改这些规则、扩大可见范围或晋升共享知识。

## C5. 写入管线

```text
触发写入
→ 绑定可信主体、任务、项目
→ 检查允许保存的类型与范围
→ 提取候选断言/事件，保留限定条件和来源
→ 严格结构校验、秘密最小化检查
→ 查重复、相同断言、冲突和替代关系
→ 形成不可变正文与拟议状态事件
→ 单写入提交协议
→ 发布有效视图，索引追赶
→ 返回已持久化/已发布的明确回执
```

去重只归并同源、同义且适用条件一致的重复记录；相反结论不能因文本相似被合并。模型提取的结构不自动获得真实性，用户更正与工具观测都要保留可定位来源。

初始写入检查与最终提交前的授权检查分开。若检查后发生撤权或任务结束，提交前拒绝。写入请求携带幂等操作号：相同操作号与相同请求返回原结果；相同号却不同请求返回冲突。

## C6. 单写入、提交、审计与对外可见

采用一个部署级持久单写入者管理组织对象变更。成员并行计算，写入排队。必须能识别重启后的旧写入者并禁止双主，不能只依赖进程内锁。

**三个概念：准备完成、业务提交、对外发布。**“业务已提交但审计最终回执未完成”是可恢复中间态，不向调用方报告正常完成，也不让新状态被普通读取使用。

推荐协议如下：

1. 验证操作号、前态、当前权限与任务有效性，分配提交序号；准备正文和事件清单。
2. 正文先写到 staged，完成结构与摘要校验，经经过验证的文件写入/刷新流程保存为最终不可变修订。此时没有提交记录，普通读取仍看不到这些材料。
3. 审计追加“操作准备”，带操作号、主体、对象引用、依据和材料摘要；必须取得持久化回执。该记录明确不声称成功。
4. 在同一串行提交边界内，重新核对最新授权、任务有效性、授权期限和预期状态版本；检查与提交之间不得插入其他会改变判定的已提交变更。随后底座追加完整业务 COMMIT，引用全部材料、状态事件、预期前态、授权版本与审计准备回执。**唯一业务提交点是经验证且持久化的 COMMIT。**一次多对象变化以同一提交清单为生效单位。
5. 先更新内部 committed_view；删除、撤权同步阻断所有受限读取，失效及替代同步阻断把旧证据作为当前有效事实返回。合法历史读取按 D4 的模式规则处理。普通读取仍使用 published_view，不能看到尚未发布的新增内容，也不能通过旧视图继续读取已被阻断材料。追加可幂等恢复的审计最终结果；失败则相关范围进入 recovering，由恢复协调器补齐。
6. 审计结果齐备后更新 published_view 并推进可发布水位。首版在审计待补齐期间暂停后续写入，使 publication_seq 始终表示已完成发布的连续提交前缀。索引可异步追赶，但当前撤权/删除/失效遮罩必须同步生效。
7. 返回 operation_id、commit_seq、publication_state、对象版本与 indexed_seq。索引落后可明确标记 pending；后续读取必须扫描差量或等待，不静默漏掉新记录。

业务记录保存状态事件和受控对象引用；审计保存事实与结果。业务状态从 COMMIT 重建，审计不能擅自使状态生效。审计的可信追加入口不再经由“业务写入→再审计”的循环，也不接受成员任意写入成功结果。

追加 JSONL 必须使用可校验的记录边界、序号、长度/摘要等机制识别损坏和不完整尾记录；文件以换行结束不等于已经可靠刷盘。中段损坏时停止重放并恢复，不跳过后继续猜状态。完整检查点只能加速回放，不能覆盖更新的提交与删除记录。

这是一份协议规格，不预先承诺特定 Windows 文件系统上的改名、刷新或锁行为。实现阶段必须选定实际存储适配器，并验证进程崩溃与断电模型下的持久性；跨文件改名不能被当成天然多文件事务。审计不可写、磁盘满、授权记录不可读时，拒绝新的受影响变更并通过可用的独立告警通道提示，不能承诺“磁盘坏了仍一定写得下日志”。

## C7. 崩溃与索引落后时的确定行为

| 发现的持久状态 | 恢复行为 |
|---|---|
| 仅 staged 或孤立正文，无 COMMIT | 不生效，隔离待清理；按既定临时文件保留策略处理，不删除用户有效对象 |
| 审计有准备，无 COMMIT | 记录操作未提交/中止，正文不可见 |
| COMMIT 完整，最终审计缺失 | 先应用有效删除与撤权信息，再校验仍应保留的引用与摘要，补最终审计；补齐前相关范围不开放 |
| 正文已被有效删除范围覆盖 | 缺失载荷标记为按授权清理，不从备份补回；pending_delete 始终禁读 |
| COMMIT 损坏，或未被合法删除覆盖的正文缺失/摘要不符 | fail-closed，报告损坏；从有效备份/副本恢复，不能默默忽略 |
| 已提交并审计，索引落后 | 读取当前有效态，扫描允许范围差量并合并；超出预算则明确等待或不可完整查询 |
| 仅索引/视图损坏 | 删除派生索引后从真源重建；不丢正文，不改变提交历史 |
| 外部动作回执丢失 | 结果未知，查目标系统或升级处理；存储事务不能回滚外部世界 |

恢复时先验证提交记录、取得更新的删除/撤权登记并折叠限制，再核验仍应保留的载荷。不能按旧创建记录逐一要求所有历史正文都存在，否则正常删除会被误报为损坏。删除记录本身必须可验证，不能用随意缺失文件冒充已获准删除。

视图记录 view_seq，索引记录 indexed_seq、schema_version、tokenizer_version、config_version。一个查询绑定明确的读取序号 s；旧索引条目先按查询模式和当前权限/删除状态过滤，再将 indexed_seq 到 s 的可读差量评分合并。历史模式可能需要建立临时时点视图或扫描允许的历史修订，不能仅从当前有效索引推断历史。索引进度不能伪装成知识截止时间。

授权与删除采用当前限制，不能冻结在旧快照。注入时如 relevant state_seq 已变化，重新取得有效证据或明确中止。不能仅替换引用编号、继续使用依赖旧事实的结论。

## C8. 删除、血缘与备份

| 方案 | 做法 | 选择理由 |
|---|---|---|
| **A，推荐** | 先持久删除标记并立即禁读，再按血缘和副本清单清理 | 本地可实现，删除范围与状态可解释 |
| B | 敏感对象独立加密，通过销毁密钥加速不可读化 | 可作增强；不能清掉明文索引、缓存和已经外发的副本 |
| C | 删除整个项目及其全部后代 | 范围直接，但损失大，仅适合明确的整项目销毁要求 |

删除须有主权者授权或其明确预授权的保留规则。先提交 pending_delete/tombstone，使当前查询、历史查询、引用展开、缓存和待注入证据全部拒读，再处理正文各修订、提取片段、词面索引、临时材料、受控备份和携带敏感内容的派生记忆。

源对象进入 pending_delete 时，同步阻止依赖它且尚未通过删除影响复核的派生摘要、记忆和待发布产物进入读取、注入与输出。可通过查询当前血缘中的祖先删除标记实现，物理清理随后进行；血缘不完整或无法确认时保守隔离相关对象，不能留下“原文禁读、旧摘要仍可读”的空窗。

如果派生知识能从独立且允许保留的来源重建，可重新生成并验证后保留。不能只删来源引用，却留下由敏感来源生成的正文。纯统计不必无条件删除，是否包含或可推导被删信息需单独判断。

审计保留最小删除凭据：随机对象 ID、授权依据、操作结果、清理覆盖范围；不保留被删原文或可枚举的敏感标题。删除登记是受保护的控制数据，不参与普通检索。备份清单只记范围与进度，不复制正文。

_删除登记/ 是有效 COMMIT 中删除与撤权事件的受保护导出副本，包含原操作号、提交序号、范围和可验证提交凭据，不独立产生或撤销决定。正常运行以提交事件为准；恢复旧备份时，经核验的更新登记作为只收紧访问的恢复遮罩，不能被旧备份覆盖。导出由同一可信底座完成并记录覆盖水位；登记未保护到所需水位前，不宣称备份恢复已能遵守最新删除。完整性或水位不明时，相关恢复范围保持离线。

备份包含某个完整提交边界内的正文、提交记录、治理状态与必要清单。恢复后必须先应用备份之后的最新删除/撤权登记，再重建索引并开放服务。最新删除登记应与日常备份分开保护；若它丢失，不能保证旧备份不会复活敏感内容，此时保持离线并明确该限制。

“已从检索隐藏”“在线副本已清理”“备份待到期”“受控副本全部清理”分别报告。无法收回已进入模型上下文或外部接收者手中的内容，后续读取与外发可停止，但不能宣称消除已经发生的阅读。

## C9. 容量、整理与运行边界

正文和事件按月或数量分片；单个正文保持适当断言粒度，避免一条记录无限追加整段聊天。视图和索引可增量更新，定期重建用于核对一致性。检查点不可作为删除旧事实的隐式授权。

后台整理只能提出合并、降权、候选能力和共享知识，不就地改已提交正文。空间不足先清可重建缓存与经过授权的临时材料，压缩索引；继续不足则拒绝新写并告警，不静默丢旧记忆。正文删除、事件保留期与备份清理由明确保留策略决定。

性能不以文档数量作未经测量的硬保证。先测写入尾延迟、完整重建耗时、差量扫描耗时和磁盘占用；若持续达不到本机服务目标，比较调整分片、换检索实现与放宽数据库约束的实际成本。

## D1. 推荐管线与替代选择

```text
识别召回需求
→ 绑定可信主体、当前任务和项目
→ 求允许范围，取得有效态水位
→ 解析实体、技术字符串、时间和查询类型
→ 在允许集合内精确匹配/中文 BM25/按需二元组
→ 融合、版本归并、来源去重、补齐冲突
→ 返回带版本和来源的候选证据包
→ 上下文装配器按预算选取，必要时补查一次
→ 注入前复核当前权限、删除及有效态
→ 回答附来源；使用反馈与事实更新分开
```

| 决策 | A | **B，推荐** | C |
|---|---|---|---|
| 触发 | 每轮全查：简单但费钱、易污染 | 规则触发 + 显式按需请求：可解释、成本低 | 全由 LLM 决定：灵活，但波动和额外调用多 |
| 范围 | 全库搜完再滤：容易暴露标题、片段、缓存 | 查询前限制 + 读取/注入再检查：代价是索引需支持作用域 | 每个岗位复制库：隔离直观，但撤销和更新副本复杂 |
| 中文检索 | 单路 BM25：保留作基线 | 中文词、完整标识符、按需字二元组：适合未知词补漏 | 立即上向量：增加资源、同步与评测成本 |
| 融合 | 原始分数相加：分布与量纲难解释 | RRF + 来源去重 + 冲突保留：简单、可回归 | LLM 全量重排：更贵、更不稳定 |
| 注入 | 固定前 N 篇全文：长文挤占预算 | 有限证据包与原文锚点：需要打包逻辑但可追溯 | 只注入摘要：紧凑但可能丢条件和反例 |
| 补查 | 一轮后直接答：快，多跳易漏 | 根据明确缺口最多再查一次：成本有界 | 搜到满意为止：停止条件和费用难控 |
| 反馈 | 高频使用就提可信度：容易自我强化 | 使用统计和证据更新分开：更可靠 | 全部人工审核：小库可行，用户负担大 |

## D2. 什么情况下查什么

| 触发 | 查询内容 | 默认不做 |
|---|---|---|
| 新任务或项目切换 | 当前项目有效决定、相关偏好、所需岗位知识 | 不载入其他项目和完整岗位历史 |
| “上次”“以前决定”“沿用” | 对应实体、任务与时间的知识/经历 | 不直接把旧回答当事实 |
| 出现错误码、路径、对象 ID | 精确匹配相关经历与修复证据 | 不搜索全量审计原文 |
| 证据缺口或冲突 | 缺失关系、来源引用、相反结论 | 不扩大项目权限 |
| 仅依当前输入可完成的改写、计算 | 可以跳过记忆检索 | 不为了流程完整强制召回 |

当前正式约束与任务验收标准由受控路径加载，不与记忆抢 BM25 排名。能力可并行解析，但作为规程引用单独展示。

## D3. 查询接口与服务端约束

以下为逻辑契约，不绑定具体编程语言：

```json
{
  "query": "上次为什么停用了旧缓存方案？",
  "task_id": "task-130",
  "project_id": "project-a",
  "purpose": "answer",
  "mode": "current",
  "valid_at": null,
  "known_at": null,
  "requested_types": ["知识", "经历"],
  "include_candidates": false,
  "budget_tokens": 2400
}
```

服务端从可信任务上下文取得 principal_id、岗位、项目、权限与本轮实例，不信任模型自报的身份。requested_types、project_id 等都是请求，不能扩张已授权范围。

mode 可为 current、historical、investigation；历史与调查模式需要对应读权。valid_at 是事实适用时间，known_at 是“截至某时当时知道什么”。历史回放仍执行现在的权限和删除限制。

默认范围：当前项目允许读取的知识/经历 + 当前岗位已发布知识 + 相关且可读的部署偏好。默认排除其他项目原文、候选、归档作答、审计、旧系统数据与复核者私有资料。复核者按本次复核另行授权。

显式跨项目读取提供三个可行选择：完全关闭、每次范围授权、长期项目对共享。**推荐保留接口但默认关闭，仅由主权者按来源项目、用途、任务、对象范围和期限授予单次读取。**完全关闭可作为首版未实现该接口时的状态；长期白名单适合稳定协作，但当前容易扩大范围。单次读取不自动授权复制进当前项目、跨项目发布或永久保留摘要。

返回状态区分 ok、no_support、needs_clarification、restricted、index_pending、unavailable、budget_exhausted。索引或权限状态不可用时，不能返回普通“0 命中”。被拒绝对象的标题、存在性与命中数量不向无权主体披露。

## D4. 先过滤，再召回；读正文和注入时再次检查

1. 从当前政策、原任务授权上限、实例绑定与拒绝名单求可读命名空间和对象集合。
2. current 模式按当前有效态与适用时间过滤；historical 模式按 known_at 回放当时认识、按 valid_at 选择适用期，允许读取后来被替代或证伪但仍获授权保留的历史材料，并明确标为当时记录。investigation 模式可按授权检查候选和争议。现在的删除与撤权限制始终覆盖所有模式，历史失效材料不能重新冒充当前事实。
3. 索引查询和排名仅针对允许集合；受限标题、片段、词频和缓存不能先提供给模型。
4. 获取候选正文时再次检查具体对象和修订；展开来源引用也做同样检查。
5. 注入时检查权限指纹和相关状态序号。变化则剔除、补查或重组结论，不能继续引用已撤回缓存。
6. 证据已注入、答案尚未交付时，输出和后续工具动作仍须检查本轮相关权限/删除版本。发生影响本轮的撤权或删除，取消该轮、丢弃待发送结果与动作，必要时用不含受限正文的新上下文重新生成；仅删引用编号不足以清除结论中的信息。事实更正影响结论时同样重新取证。高敏感结果首版采用整体校验后交付；若使用流式输出，每批输出经过当前授权门，已交付部分无法追溯收回。

物理上可按项目/岗位发布集合/复核私有范围分索引，但同一分区内仍需对象级过滤。共享倒排索引的内部数据只由受控服务读取；统计和返回内容不应暴露无权对象。首版数据量小，可对本次允许集合计算或汇总所需词频统计；效率不足时优化分区，不放弃访问检查。

项目切换必须新建或重置模型上下文，不能只换一个 project_id 后继续沿用已带入旧项目正文的会话。Lead 的逻辑身份可以不变；运行上下文要隔离。已经被模型读取的内容无法靠缓存键“让它忘掉”。

## D5. 索引内容、分词与分块

索引只存已提交材料的派生表示：对象/修订 ID、授权分区引用、词项、词频、长度、精确标识符和必要定位；不把含正文的索引当作低敏数据。状态最终仍查当前有效视图。

普通正文使用固定版本中文分词，维护小型领域词典。技术字符串保留完整形式，再生成辅助拆分：错误码、路径、版本号、对象 ID、连字符与驼峰词。大小写敏感标识符保留原样；规范化只用于辅助召回，不改原文。

词面不足时启用字二元组，如“权限撤销”产生“权限、限撤、撤销”。这种通道有噪声，不能代替语义判断。Lucene 官方资料区分了按字二元组和按词切分的做法，参见 [CJK 分析器说明](https://lucene.apache.org/core/10_3_1/analysis/common/org/apache/lucene/analysis/cjk/package-summary.html)。这是分词设计参考，不要求项目采用 Java/Lucene。

标题、实体和受控别名形成短字段，正文形成长字段，分别产生排序。BM25 使用内置长度归一化；不再随意除一次长度。索引与查询必须使用同一分词和词典版本；版本改变要重建对应索引并跑回归。

一个知识条目通常就是一个检索单元。长经历可按完整事件或断言分块，块保留否定词、版本、时间及适用条件；块 ID 从父对象/修订派生。父对象撤权、失效或删除时全部块一起受影响。

## D6. 多路召回与排名融合

推荐首版最多使用以下四张候选列表；每张列表均在本次允许集合内生成：

| 列表 | 作用 | 起始上限，未实测 |
|---|---|---|
| 精确标识符 | 用户明确指定 ID、错误码、版本或路径 | 10 条 |
| 标题/实体/别名 BM25 | 主题和对象匹配 | 20 条 |
| 正文 BM25 | 完整事实和经历匹配 | 20 条 |
| 字二元组 | 分词漏词、未知术语或首轮证据不足时启用 | 20 条 |

各列表及并集按检索单元计数；retrieval_unit_id 由对象 ID、修订号和块锚点组成，短条目用整体正文锚点。每轮候选并集初始上限 70，去重后通常更少。完整 ID 命中优先定位对象，但仍须显示其当前有效性和冲突，不因精确命中绕过治理。

非精确列表用 RRF 融合：

```text
RRF(d) = sum_i [ 1 / (60 + rank_i(d)) ]
```

公式中的 d 为 retrieval_unit_id。rank 从 1 起，同一检索单元在每张列表中最多出现一次，未进入某列表不贡献该项。60 是初始值，需回归；RRF 用名次避免直接叠加异构原始分数，见 [RRF 原始论文](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)。它不保证对本数据一定最优。

融合后依次处理：跨列表同一检索单元归并；同源复述去重；按查询模式选择版本；冲突补齐；适用条件核对。同一父对象不同块只合并公共元数据，保留所需的各个正文锚点，不能把“决定”和“理由”误删成只剩一块。RRF 分数表示相关性，不是事实可信度。高频引用、用户点赞、比较新，都不能单独把内容升级成真。

一次查询不要生成大量近似改写列表，让同一材料因重复命中被人为加分。别名表版本化，模型建议的别名仅作为一次候选查询，不立即成为全局词典。

## D7. 冲突、时间与多跳

命中冲突组的一边，要寻找同组其他可读证据，保留冲突提示。受限来源只向当前主体显示其有权了解的信息；不能为了“展示完整冲突”泄露另一项目原文。必要证据受限时，应表述无法在当前范围确认，不能暗示不可见内容细节。

时间查询分成三类：现在采用什么、某时实际适用什么、某时我们当时知道什么。后两者可能不同。例如 10 月 8 日发现 10 月 1 日的配置记录有误，“10 月 1 日真实配置”可用后来取得的证据回答，“10 月 1 日当时的认识”则只用当时已记录的材料，并标出后来纠正。

首版每个逻辑召回请求最多总共两轮查询。第二轮只补明确缺口，例如第一轮找到决定但没有理由，或结论依赖某个测试引用。通过 source_refs、derived_from、conflict_group 的邻接索引完成有限跳转，不需要图数据库。每条边重新授权，引用展开初始上限为本次请求累计 10 条，超预算则说明证据不完整。同一信息缺口不能通过更换请求 ID 重置预算，追加工作由任务级预算规则决定。

超过预算仍无充分证据时停止，返回已有依据与缺口。不能因零命中自动打开其他项目、归档作答或旧系统数据。

## D8. 证据包与上下文装配

记忆服务返回候选、状态和引用；任务执行器内的装配器决定实际注入。证据块包含：memory_id、revision、类别、摘录、适用时间与条件、来源、证据状态、冲突信息、定位锚点。

```text
[mem-a7c2f8d1@1 | 项目知识 | 当前有效 | supported]
结论：客户端低于 2.4 时需要兼容回退。
范围：task-118 已测试的客户端与服务端组合。
来源：artifact-test-118@1，compatibility-cases。
限制：其他客户端实现尚未验证。
```

预算先满足权威约束、当前用户输入、任务状态、必要工具结果与输出预留，再分配给记忆。推荐初值：

```text
记忆预算 = min(2400 tokens, 剩余可用上下文的 20%)
证据块数量 <= 8
补充检索轮数 <= 1
```

这些都是待实测的起点；token 不等于中文字数，应使用实际模型的计数方法。两轮结果共同组装一个最终证据包，8 块与 token 限制对本次上下文中全部仍驻留的记忆证据累计生效；第二轮须替换或重新打包，不能另加一整包。即使多个片段归属同一对象，数量与 token 仍按实际注入内容核算。

预算不够时优先去重复和低相关内容，保留关键否定、版本、时间和冲突。关键证据组合仍放不下，说明不完整；确需分步取证时必须获得任务预算规则允许，不能借“分步”绕过两轮上限。不能只保留支持方。

摘要是可追溯的派生产物，不替代原文；摘要失效、删除和重建沿来源血缘传播。第一版优先抽取片段，不默认额外调用模型总结每个候选。

政策、当前用户请求、任务判据、能力规程、记忆证据分别标明来源。外部文本即使被多次摘要，也不因此转化成可信指令。回答引用的版本必须是实际读取版本。

## D9. 缓存、零命中与反馈

首版默认只在内存中短期缓存候选 ID/版本与排名，不持久缓存正文证据包。缓存键至少包括主体权限指纹、任务范围、项目、岗位发布版本、查询/时间条件、有效态序号和索引配置版本。缓存命中后仍重新检查当前权限、状态和删除。

零命中输出说明实际搜索面、时间条件与尝试口径。例如：“在当前项目的有效知识和经历，以及可用岗位知识中，经过原词与别名查询，未找到支持材料。”这只描述本次搜索结果，不宣称相关事实在世界上不存在。

若索引落后但未完成差量扫描，返回 index_pending；若权限服务不可用，返回 unavailable；若问题有多个时间或实体解释，返回 needs_clarification。不同失败不能全部折成“没记住”。

反馈记录展示、引用、验证结果、用户纠正与耗时。召回或引用次数只用于缓存/维护优先级；答案被点赞不自动修改事实证据等级。模型从旧记忆生成答案再写回，仍继承旧来源，不能成为第二个独立证明。

## D10. 初始参数清单

| 参数 | 建议初值 | 调整依据 |
|---|---|---|
| 普通记忆触发 | 新任务/历史指代/偏好依赖/错误码/证据缺口 | 漏召回与无效召回案例 |
| BM25 k1 / b | 1.2 / 0.75 | 开发集调参，固定测试集独立验证 |
| 列表大小 | 精确 10，其余每路 20 | 必要证据召回与延迟 |
| 二元组 | 按需启用 | 未知词与噪声比例 |
| RRF 常数 | 60 | 排名质量与候选覆盖 |
| 注入 | 8 块、2400 tokens、剩余上下文 20%，同时取约束 | 正确率、证据完整度与总费用 |
| 补查 | 总共最多 2 轮 | 多跳成功与额外成本 |
| 引用展开 | 初始最多 10 条 | 证据链覆盖、授权和预算 |
| 跨项目原文 | 默认关闭 | 用户明确授权的需求 |
| 候选/归档作答/旧数据 | 默认排除 | 显式调查与追溯授权 |

没有统一的 BM25/RRF 分数阈值可以直接保证事实正确。应使用是否有适用证据、是否覆盖问题、是否存在冲突来决定回答方式。参数表是实施起点，不是本机性能测试结果。

# 第五部分：贯穿案例、评测与实施

## E1. 一个完整生命周期案例

以下全部为虚构场景，用于验证协议。

| 步骤 | 操作与持久变化 | 预期召回行为 |
|---|---|---|
| 1. 项目 A 首次失败 | 记录一条经历和工具证据，未知原因不写成确定原因 | 能找到该失败，明确原因尚待验证 |
| 2. 提出原因 | 成员提出“所有客户端都要回退”的候选知识 | 默认答案不直接引用候选作事实 |
| 3. 验证收窄 | 测试发现仅低于 2.4 需要；生成带条件的新修订并激活 | 当前查询返回受条件限制的版本 |
| 4. 原因查询 | 用户问“为什么保留回退”；首轮命中知识，次轮读取测试引用 | 引用明确版本与测试范围，不泛化 |
| 5. 晋升岗位知识 | 提炼通用兼容性规律，去除项目路径，经披露与独立复核 | 项目 B 能读通用规律，不能读 A 的来源正文 |
| 6. 后来推翻 | 新工具证据推翻旧修订，追加 invalidation，派生岗位知识标待复核 | 旧索引即使还在，也不能把旧结论当当前有效知识 |
| 7. 并发撤权 | 查询产生候选后，主体读权被撤销 | 读取/注入检查拒绝该证据；旧缓存不放行 |
| 8. 敏感删除 | 用户要求删除误入来源中的个人信息；先禁读，再处理修订与派生副本 | 当前、历史与摘要不能复现被删内容 |
| 9. 恢复旧备份 | 备份早于删除；先应用最新删除登记，再重建 | 删除对象不复活；登记缺失时不开放恢复结果 |

这个案例同时验证“记得住、改得对、搜得到、用得准、隔离成立、删得掉、恢复不复活”，不能只测试第一次写入后的搜索命中。

## E2. 回归集与评价方法

建议首版建立 80—120 个本地合成或脱敏案例，作为工作量起点，不代表足以证明生产质量。采用开发集调参数，保留独立测试集；不把反复调参用过的样例继续当盲测证据。

每个样例保存查询、主体、项目、时间、允许范围、应生效版本、必要证据集合、可接受答案、禁止出现的对象与事实，以及应拒绝猜测的情况。长期记忆评测应覆盖信息抽取、多会话、时间变化、知识更新和无依据时不猜测，这些维度可参考 [LongMemEval 原论文](https://arxiv.org/abs/2410.10813)。公开研究不能替代本部署的权限与恢复测试。

| 测试族 | 必须观察的结果 |
|---|---|
| 精确实体/路径/错误码 | 指定对象与正确修订进入候选 |
| 中文别名、未知词 | 能区分分词漏召回和排序靠后 |
| 条件与否定 | 不将“不适用于新版”截成“适用于新版” |
| 当前与历史时间 | 正确区分实际适用时间和当时已知信息 |
| 历史已失效记录 | 当前查询排除；获授权的历史查询仍能看到当时认识及后来证伪状态 |
| 多会话更正 | 新会话读到更正后的事实，旧结论不继续冒充当前状态 |
| 未决冲突 | 关键两侧及冲突提示保留，不以最高分替代裁决 |
| 多跳与证据组合 | 必需的整组证据齐全；只命中其中一条不算完整成功 |
| 项目隔离、来源展开 | 通用知识可复用，来源原文仍受限制 |
| 复核私有资料 | 被验 Lead 不能通过索引、ID 或历史路径读取 |
| 召回到注入间撤权 | 已选材料在最终注入前被阻止 |
| 注入后、输出前撤权 | 取消受影响生成与工具动作，从清洁上下文重做，不能只移除引用 |
| 删除与旧备份 | 删除内容不通过历史、摘要、缓存或恢复重新出现 |
| 索引落后 | 失效立即过滤，新记录差量合并；不能把未扫描当零命中 |
| 注入攻击 | 原文、摘要和多级派生中的越权指令均不改变实际授权 |
| 自我强化 | 同源反复引用不增加独立证据数或自动激活 |
| 多块与累计预算 | 同一经历的决定/理由均可保留；两轮满额且补冲突后，最终包仍不超累计预算 |
| 原始作答与旧数据 | 默认检索排除；显式入口仍严格授权 |
| 无证据、错误前提 | 不编造用户经历；说明当前证据不足 |
| 提交崩溃/磁盘满/双写入者 | 没有假成功、不丢已确认提交、不出现两个有效写入者 |
| 审计故障 | 已提交待恢复有明确状态，不能被客户端盲重试 |
| 失联与恢复 | 业务证据可记，共享晋升待决；重新上线不批量自动批准 |
| 反讨好 | 相同事实配相反用户立场，不无证据改变结论 |

指标分三层，不能用一个最终答案分数掩盖失败：

| 层次 | 指标 |
|---|---|
| 检索 | Recall@k、必要证据集合完整召回率、排名质量、失效材料误入率 |
| 回答 | 事实正确率、引用支持率、条件保留率、冲突处理正确率、无依据时不猜测比例 |
| 系统 | 越权暴露数、撤权/删除正确性、提交恢复、延迟、磁盘与重建开销、注入 tokens、总费用 |

至少对比：单路 BM25；推荐多路词面；相同预算下的简单历史选取。三者都使用相同授权和有效态过滤、相同回答模型和上下文预算。不能把更多 token 或更多模型调用的收益说成索引改进。

权限、删除、预算与提交恢复是确定性门槛，出现违规即阻止相应能力上线；有限测试通过仍不代表绝对无漏洞。质量改善报告样本量、分组结果及失败样例，小样本不作普遍有效的统计结论。

## E3. 推荐实施顺序

| 阶段 | 交付物 | 退出条件 |
|---|---|---|
| 0. 固定契约 | schema、权限矩阵、状态机、任务/记忆版本语义、删除与恢复规格 | 例外和冲突有唯一解释，关键样例已写成验收条件 |
| 1. 可靠写与精确读 | 单写入者、不可变修订、提交/审计回执、按 ID 读取、状态折叠 | 崩溃、重复请求、撤权、失效和删除测试通过 |
| 2. 单路词面基线 | 有效态过滤、中文分词、BM25、证据包与预算 | 索引可重建，零命中与不可用能区分，建立本地质量基线 |
| 3. 提高召回 | 精确词、多字段、别名、按需二元组、RRF、有限补查 | 在相同预算下有可观察改善，不能牺牲隔离和更新正确性 |
| 4. 跨任务积累 | 候选准入、偏好、冲突裁决、能力候选、岗位知识提炼 | 不出现同源自证、跨项目泄露和未经审定的共享晋升 |
| 5. 运营能力 | 维护窗口备份、恢复演练、删除覆盖、监测与参数回归 | 恢复可验证，成本与质量数据足够决定是否扩大自治 |

每阶段先端到端打通少量真实任务，再扩组件。第一版可以一个程序、多个模块，保持八件职责边界；当前不需要为了组织名称建立八个网络服务。

备份首版推荐明确维护窗口：暂停新写，完成在途提交与审计，冻结完整水位，复制并校验材料，备份标记完整后恢复写入。在线备份可后续做，但必须协调并发写入与删除；中途失败的备份不能进入可恢复清单。

## E4. 何时重新考虑被暂缓的方案

| 方案 | 重开条件 | 必须比较的代价 |
|---|---|---|
| SQLite 或其他事务存储 | 文件提交器维护成本、并发需求或恢复复杂度已超过原约束收益 | 运维、可读性、迁移、备份和删除一致性 |
| 向量/混合检索 | 满足原稿的候选缺失实测与算力约束解除两条件；词面改进仍有明确遗漏 | 同预算召回增益、中文/技术字符串表现、索引删除与权限过滤 |
| LLM 重排 | 候选已有答案，排序错误占主要失败，且预算可承受 | 稳定性、额外时延、提示注入面与真实答案收益 |
| 图数据库 | 受控 refs 多跳成为主要需求且邻接索引维护已困难 | 运维、关系正确性与跨边授权 |
| 每实例容器/账号 | 需要执行不可信代码或更强宿主隔离 | 启停开销、凭据与文件权限管理 |
| 多模型会审 | 独立证据机制后仍存在可复现共同盲点，且任务价值足够 | 费用、数据边界、模型差异与漏检率 |
