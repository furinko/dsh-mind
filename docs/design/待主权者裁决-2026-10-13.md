## 1. 债⑥ 跨账本同毫秒撞 id

**现状**：记忆 id 种子 = 类+主体+时刻，**不含项目 scope**；两项目同毫秒同主体同类 ⇒ 同 id ⇒ 跨账合并读面把两条记忆静默合一。触发面极窄（当前单项目部署根本碰不到）。
**为什么你定**：修法是 id 种子加 scope = **数据模型变更**，会改既有 id 形状与引用面。
- **甲：维持现状**，登记触发器（出现第二个项目且同类同毫秒写入现场时回头修）。
- **乙：现在就改** id 方案，一次性把 scope 纳进去（存量 id 不动，只改新 id）。
- **建议：甲**。窄到没有现场，乙的迁移成本买的是用不上的保险。

## 2. 债⑦ archiveAnswers 锁外读

**现状**：归档先锁外读账、再锁内追加状态行——两次之间新写入的作答**漏一次归档**（不丢数据，下轮结账补上）。
**为什么你定**：修 = 读写搬进同一把锁，扩大 `#appendLedger` 职责，要新门禁测试；属于「低频路径要不要买并发保险」的口味问题。
- **甲：维持**（接受「漏一次、下轮补」）。
- **乙：读写同锁**（结账路径的归档一次性收净，约半天工：改动 + 一条并发门禁）。
- **建议：乙**。成本小，且「结账把作答归零」本来就是心智里的硬承诺，不如坐实。
