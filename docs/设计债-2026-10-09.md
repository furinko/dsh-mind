## ① `readonlyCommand` 生产零调用点（未接线）

**债**：复核者的「只读命令白名单」（`ReviewProtocol.readonlyCommand`，`src/review.js:290`）**没有任何运行时调用点**——
白名单本身已经修实（`node --test` 已移除，跑测试＝写副作用），但没有门禁在跑它。

**证据（两处 grep，各自的分母）**：

```

$ git grep -n "readonlyCommand" -- src lib components
src/review.js:290:  static readonlyCommand(command) {      ← 唯一命中＝定义本身 ⇒ 生产调用 0 处
# （另有 5 处测试引用在 test/entry-bounds-w3c.test.js、3 处文档引用在 DESIGN-MAP/INTERFACES/docs，不计入生产面）

# 面 2：宿主安装目录（复核补搜）
$ 在 C:\Users\kuro\.dsh\profiles\desktop\node_modules\dsh-mind 下只搜 src/ 与 lib/（排除 test）
C:\Users\kuro\.dsh\profiles\desktop\node_modules\dsh-mind\src\review.js:290   ← 同样只有定义
```

**动作面也没有承载它**：`lib/actions.js` 的 `ACTIONS`（第 17–54 行）里没有对应动作名。

**为什么现在不修**：接线属**设计决策**——复核者的命令面在哪（模型侧还是人侧）、谁执行、闸挂哪一层，都没有裁决。

**什么时候必须回头修**：出现「复核者要跑命令」的真实需求，或复核者命令面进入设计/裁决时。

## ③ `bus.summary` 接投影前必须做「免审计 / 聚合档」（未接）

**债**：`bus.summary`（`src/bus.js:236-244`）对**每个线程**调一次 `read()`；而契约 B（`13a3421`）之后，
`read()` 每次调用落**一条**「只读服务调用」审计（`src/bus.js:107-121`）。若直接把它接进看板轮询，审计面会被投影读数淹没。

**证据**：
- 当前**零调用点**：`git grep -n "summary("` 全仓只命中 `src/bus.js:236` 定义本身；
- 轮询间隔：`components/board/lib/client.js:1380` → `var POLL_MS = 3000;`；
- **定量（推算，不是压测）**：86 400 s ÷ 3 s = **28 800 次/天**；再乘「每次投影要读的线程数」——
  复核给的 ≈**14 万条/天**对应「按 5 条线程算」：28 800 × 5 = 144 000。**分母＝线程数，随项目变化**；
  这个系数（5）我没能在源码里钉死，属推算，写在这里是为了可复算，不是当实测读数用。

**为什么现在不修**：summary 还没接投影（不接就没有噪音）；真要修的是「投影类批量读」的**免审计或聚合档**，
这属于策略面设计（哪些读算投影、免审计的边界在哪、谁批准），不该顺手改。
**什么时候必须回头修**：任何把 **过审计的 `read()` 循环**（或 `summary`）接进轮询/看板**之前**。
> ⚠️ **门口径订正（2026-10-10 · 主人拍）**：原措辞里的「per-thread `read` 循环」**不设限**会把 `readRaw` 也算进来，而 `readRaw` 是**故意不过审计**的内部读（`src/bus.js:127-130` 自陈为躲审计噪音）⇒ 不产生本条的债（审计面被投影读数淹没）。复诊实测：`src/org.js:154-157` 的 per-thread `readRaw` 循环**已在**看板每 3 秒的投影里，但审计面 `只读服务调用` **0 命中** ⇒ 字面已满足、**实质未到点**。

## ④ `#lineageIndex` / `bus.readRaw` 每次全量读账（成本面）

**债**：血缘索引与线程读取都是**每次调用全量读账**，账本大了是线性成本。

**证据**：
- `src/memory.js:786-793`：`#lineageIndex()` 扫 `MEMORY_KINDS × (跨项目 + 全部项目账本)` 的**全部行**再建索引（纯投影、不落盘——不变式 #4「可重建、不另立真源」）；
- `src/bus.js:135-148`：`readRaw()` 读整条线程账本再按 id 折叠；
- 调用面：讨论预算闸**每次发言**都 `readRaw`（`src/debate.js:117`）；`purge` 对每个下游项调一次闭包（`src/memory.js:801-803`，每次重建索引）。

**为什么现在不修**：当前数据量（记忆个位数、线程几十条）线性成本可忽略；**先测瓶颈再动**——
与《现状核对》§四 第 4 条同款纪律（「现在记忆条数是个位数，任何性能论证都还没有数据」）。
**什么时候必须回头修**：单账本行数上万，或血缘查询/线程读进入热路径（例如看板每轮 poll）时——
届时考虑索引缓存 + mtime 失效，或把血缘索引落成「可重建的派生件」（不能变成第二真源）。
> ⚠️ **门口径订正（2026-10-10 · 主人拍）**：本条以「**单账本行数上万**」为准；原措辞第二半「血缘查询/线程读进入热路径（例如看板每轮 poll）」**降级为已发生的事实记录**、不再是触发条件——该事实今天已成立（`src/org.js:154-157` 的 per-thread `readRaw` 循环就在看板每 3 秒的轮询路径上），但因账本为空（0 行）**成本为 0**；量上来时它才是真成本。

## ⑤ `withLock` 残余 TOCTOU（已知边界）

**债**：`finally` 里「读回锁文件确认令牌 → `rm`」之间有一个极窄窗口——确认之后、删除之前，
锁文件若被强夺者重建，删掉的仍可能是新持有者的锁。

**证据**：已登记 `INTERFACES.md` §2.19 第 1 条（647–653 行）：**实测分母 = 复核 150 轮 + 40 轮实机压测，未命中**；
读码确认窗口存在（两次独立系统调用之间没有原子性可借）。现有三道防线：①「验后删」（`e37f9df` 批1）；
②进程内 `serializeByKey`；③stale 强夺 + `onSteal` 留痕。

**为什么现在不修**：要真原子化得换 `flock` / `O_EXCL` 目录锁这类**跨平台语义不同**的机制，
收益（窗口从"极窄"降到"零"）与代价（Windows 语义差异 + 已实测的锁易主留痕路径要重写）不成比例。
**什么时候必须回头修**：命中一次（留痕可查）／临界区变长／跨进程写者变多时。

## ⑥ 跨账本同毫秒撞 id（待裁决）

**债**：记忆 id 的种子是「类 + 主体 + 时刻」，**不含 scope**；同一毫秒、同一主体、同一类在**两个不同项目账本**里会算出同一个 id，
而跨账合并的读面（`query` 的跨项目+项目扫描、`stats()` 跨账 fold）按 id 归并 ⇒ **两条记忆静默合一**。

**证据**：
- id 形状：`src/kernel/ids.js:44-61`（`<kind 前缀>-<slug(seed)>-<短哈希>`，`at` 参与哈希）；
- 查重只在**单本账本**内：`src/memory.js:856-866` —— `const rows = await readJsonl(file); const 已用 = new Set(rows.map(...))`（`file` 是一本账）；
- 实例内递增只管本实例：`src/memory.js:805-820`（`#lastStamp` 是实例字段）；
- 合并 fold 确实存在：`src/memory.js:339` 起的召回面与 `stats()` 跨账合并（`93109b1` 批2 ⑪）。

⇒ 触发条件是「两项目 × 同毫秒 × 同主体 × 同类」同时成立——窄，但不是不可能。
（批1 已在**同账本**内堵过：锁内查重 + bump 时刻重算，`test/concurrency-w3.test.js` 有断言。）

**为什么现在不修**：修法（id 种子加 scope）会改既有 id 形状与既有引用面，属**数据模型变更**；
单项目部署下根本触发不到。
**什么时候必须回头修**：出现第二个项目、且同类记忆在同一毫秒写入的现场；或做 id 方案整体变更时一并带上。

## ⑦ `archiveAnswers` 锁外读（待裁决）

**债**：归档时先**锁外**读整本作答账，再**锁内**逐条追加归档状态行——两次之间新写入的作答不会被本次归档覆盖。

**证据**：`src/memory.js:615-626`：

```
const rows = await readJsonl(file);                       // ← 锁外读
const open = rows.filter((row) => !isStateRow(row));
...
await this.#appendLedger(file, open.map(...追加 '归档' 状态行...));   // ← 锁内写
```

**后果**：**不丢数据，只漏一次归档**——那条作答仍留在召回面，直到下一次结账/归档调用（`tasks.settle` → `MemoryService.archiveAnswers`，`b30c704` ③）。

**为什么现在不修**：把读也搬进同一把锁（read-modify-write 合一）会扩大 `#appendLedger` 的职责（读+写一体），
需要一条新的门禁测试；而归档是结账路径（低频、Lead 触发），当前没有并发现场。
**什么时候必须回头修**：结账与成员交卷并发出现，或把「一次结账把当时全部作答归零」写成硬承诺时。

## ⑧ 服务面 `发件` 未收紧（动作面已封）

**债**：`bus_send` **动作面**已封（`args.发件` 一律忽略，handler 恒以主体链真实 id 为发件人），
但**服务层** `bus.send` 仍接受调用方给的 `发件`——因为内部编排需要它（unlock 广播、讨论轮边界、converge 末位表态）。

**证据**：`INTERFACES.md` §2.15（545–550 行，「系统类型消息仅系统主体可发」+「动作面发件不自报」）；
`src/debate.js:171-179`（轮边界用 `subject: { id: 'system', kind: '系统' }`）、`src/debate.js:210-218`（converge 发件 `lead`）。

**为什么现在不修**：服务面收紧会让上述内部编排**没有表达方式**——要么改签名让编排传主体、要么给「系统主体」一个内部构造器；
这是接口设计（谁可以扮演系统），不该在安全修复批次里顺手改。
**什么时候必须回头修**：新增任何「模型参数直通 `bus.send`」的路径之前（那时服务面就是新的伪造入口）。

## ⑩ `useStore` 的宿主假设未验证（待裁决）

**债**：看板客户端有一个**假设**——「宿主给插件的 React 里 `useEffect` 很可能是空实现」；
它不是机制性验证，而是对真机现象的推断。`hook()` 兜底只覆盖「hook 缺失」，覆盖不到「是函数但不跑回调」。

**证据**：
- `components/board/lib/client.js:1360-1376`：注释自述观察（真机上面板/设置页停在初始态，而点「保存」能动 ⇒ `useState` 好、`useEffect` 坏）；
- `components/board/lib/client.js:64-85`：`hook()` 检测 `typeof fn === 'function'`，是函数就用 ⇒ 「是函数但不跑回调」这条路径的兜底**不生效**；
- 缓解已在：取数移出 `useEffect`（裸 `setInterval` 轮询，`client.js:1359-1382`）⇒ 即使假设成立，也只少一层增强。

**为什么现在不修**：要验证得能拿到宿主 React 实例（跑一次真实挂载探针），本仓测试环境给不出；
改法只剩「关键路径不用 `useEffect`」——**已经做到**了。
**什么时候必须回头修**：宿主升级 React／出现第二家宿主时，或要把关键路径重新挂回 `useEffect` 时。

## ⑫ `needsQuote` 触发集与读侧规则互为配对（已知边界·不变式）

**债（配对不变式，不是待修缺陷）**：`formatFrontMatter` 写侧的「需要时才引号化」触发集
（含 ` # ` / 行首 `#` / 换行 / 引号 / 反斜杠 / 首尾空白 / 空串 / 整值形如 `[...]`）与读侧规则
（剥引号、切行内注释、切数组）**互为配对**：改一侧必须同步改另一侧。

## ⑰ `bus_send`（动作面）可直灌会审讨论线程 ⇒ 绕开 `debate_say` 三道闸（**登记 + 已办 2026-10-10**·独立复核实证）

**债**：讨论线程（线程 = **开过讨论段的节点 id**）的发言只有 `debate_say` 一条正路——那里有类型闸（分歧/表态/答复）、两道预算闸（每轮消息数 / 每人每轮字符，快照冻结）与发言权判据（参与者或强制反对者）。但 `bus_send`（动作面 = **模型可达面**）对线程**零归属校验**：任何主体可把消息直接灌进讨论线程，三道闸全部绕开；而预算判据（旧：类型 ∈ 三种 且 `发件 !== 'system'`）又会把外人灌的水**算进本轮**——于是灌水不只是"多几条消息"，而是**把参与者的闸占死**。

**证据（2026-10-10 独立复核脚本实测，工作树含未提交改动）**：上限「每轮 2 条 / 每人 10 字」下**直灌 11 条全部落线**，参与者随后 `debate_say` 被拒（预算被外人占死）。本批把攻击**原样钉成回归**（`test/debate-guards.test.js`）：

**修法**：

  （⚠️ 上面这行是**当时**的落点，别当现状读：批c 补漏之后判据已抽成 `拒讨论线程直灌`（单点，两个 handler 共用）、
  查节点的键也改成与落线侧同源的 `线程等价键()` —— 见下面「⑰·补 P2 / P3」。）
- **乙（服务面纵深防御）**：`本轮发言(messages)` → **`本轮发言(messages, 名单)`**（`src/debate.js:365`，名单 = `预算名单(讨论)` = 参与者 ∪ 反对者，`:397`）。三处调用点传**同一份**名单：`say`（`:188`）、`round`（`:251`）、`src/workbench.js` 讨论小节（`:390`）。`本轮发言` 的名单**必填**：漏传 ⇒ `InvalidBody` 响亮失败（漏传若被当空名单，预算两道闸静默失效 = fail-open）。

**诚实边界（必须读·批c 补漏后订正）**：**甲堵的是动作面**（不是「服务面」）。**服务面 `bus.send` 仍可往讨论线程发消息**——`unlock` 广播、轮边界、`converge` 末位表态**都靠它**，那是有意的编排通道（照旧是 ⑧ 那条债，未变）。**不许把它读成「已彻底修复」**：`A2-回归` 里那句「11 条真落线」就是服务面仍开放时的如实读数。

> ⚠️ **订正（2026-10-10 · 批c 独立复核第二次攻破，实测）**：本段原先写的是「**模型可达面只有动作面 ⇒ 甲足够堵住「模型能灌水」**」——**这半句已被证伪**，如实口径是：

### ⑰·补 P2 / P3（2026-10-10 批c 补漏·独立复核实证，已办）

**P2 —— `bus_unlock` 是动作面第二只「往线程落消息」的手（实测攻破）**

- **实测读数（修前，本轮复现）**：`bus_unlock{id:讨论节点, 线程:讨论节点, 内容:'P2-ATTACK-A'}` ⇒ **放行**，线程里落线
  `发件=system / 类型=广播 / 内容=攻击者原文`；**同一条重复调用两次 ⇒ 落 2 条（无去重）**；
  `id` 换成**别的已交卷节点**、`线程` 指成讨论节点 ⇒ **依然放行**（落 3 条）。三种形态合计 **3 条**落在讨论线程上。
- **危害的边界（不许夸大）**：类型 `广播` **不在** `DEBATE_SAY_TYPES` ⇒ **不占预算**；也**伪造不了轮边界**
  （类型 `系统` 只许 `kind==='系统'` 主体，`src/bus.js` 那条闸仍拦成员）。危害是**往讨论线程注入伪造的系统广播**（内容可控、可重复）。
- **修法**：判据收成**一处实现**——`lib/actions.js` 的 `拒讨论线程直灌({org, 项目, 线程, 入口})`，`bus_send` 与 `bus_unlock`
  **各自只留一行调用**。`bus_unlock` 里的**顺序**是先判**落点**（线程是不是讨论线程）、再判**资格**（齐卷）：
  落点判据与事件流无关，先立住。文案沿用甲那一套（并把**哪只手**写进 `message` 与 `detail.入口`）。
- **正对照（实测，正常运行路径不许被误伤）**：`bus_unlock` 对**普通线程** ⇒ 放行、广播落线 1 条；
  `bus_unlock` 对**未开讨论的节点**（`线程 = 节点 id`，这正是它的正常用途：全员交卷后解锁广播，那时还没有讨论段）⇒ 放行、广播落线 1 条。

**P3 —— 甲命中用的键与落线用的键不同源 ⇒ 大小写别名绕过（实测攻破）**

- **实测读数（修前，本轮复现）**：`线程 = <讨论节点id>.toUpperCase()` ⇒ `tasks.get(别名)`（fold Map 精确键）**命不中**
  ⇒ 甲**放行**；而 `layout.busThread` 把线程名直接 join 进路径、本部署载体是 **NTFS（大小写不敏感）** ⇒
  消息**落进同一个文件**（实测：`readRaw(真 id)` 读到那条，文件实名 = 大写那个写法）。**类型闸一起废**：
  攻击用的是 `类型:'交卷'`（讨论类型**之外**的），照收。
- **修法（先确认落线侧的规范化，再让两边同一个）**：落线侧的等价类是**文件系统给的**（`busThread` 自己不折任何东西）。
  于是把它写成**一处声明**：`src/paths.js` 新增导出 `线程等价键(thread)`（就放在 `assertPathSegment` 旁边，
  `busThread` 的注释指向它），`lib/actions.js` 的判据**只**用它 —— 先精确命中（不改变既有语义），
  没命中再按等价类找。口径**不多不少**：
  - **只折大小写**（`toUpperCase`，与 NTFS 的比较表同向）；
  - **不做 Unicode 规范化**：NTFS 不折 NFKC，折了会让判定比落线**更宽**（`①.jsonl` 与 `1.jsonl` 是两个文件）⇒ **误伤**；
  - **不折分隔符/冒号**：`assertPathSegment` 已在落线侧把它们拒掉 ⇒ 那一面没有别名可绕。
  - ⚠️ 已知边界：非 ASCII 大小写（`ß`/`ı` 这类）与 NTFS 的比较表未必逐字符同向；本部署的线程名/节点 id 由 `slugOf`
    生成（字母+数字+哈希），不落在这条边界上——真出现时按**当时载体**的比较表复核。
- **正对照（实测）**：普通线程的大小写变体（`T-P3-Normal` / `t-p3-normal`）⇒ 都放行、都真落线；
  且在**本仓载体**上这两个写法只对应**一个**线程文件（落线侧等价类的实测，即判定侧照它折的理由）。

**两道拦阻（为什么「有承载位」不等于「有来源」）**

- **拦阻①（格式无契约）**：`label` 的语义是**自由文本**。要取出岗位就得硬编码 `<岗位名>:<成员名>` 这个**形状**——而那个形状是**自制客户端侧插件**的约定（任务书点名 `agent-roles.js:1018-1021`，本批**明令不许读**）⇒ 我**连分隔符是不是 `:`、岗位名本身能不能含 `:`、有没有 trim 都无法核实**。硬编码一个核实不了的格式，正是任务书明令的「**不许硬造**」。
- **拦阻②（信任等级）**：one-shot 路径的 `label` 就是**模型**写的 `description`（见上表 #6）。拿它当岗位 ⇒ 用**模型可控字段**声明身份 ⇒ 那正是 ⑳ 门① 堵掉的洞（`args.role`）**换了个字段名**。而且日志里「宿主组合的岗位 label」与「模型写的委派描述」**逐字节同形**、没有来源标记 ⇒ 内核**无法分辨** ⇒ 这是 **fail-open** 方向（§12.1 不许）。唯一可能的判别器是 descriptor 的 `provider` 名（自制插件自己的 provider），但那个名字只能靠**读被禁的文件**或**猜**得到。

## ㉒ 实例键退化：`'session-' + 会话id.slice(0,8)` ⇒ 恒 `session-session-`（**登记 + 已办 2026-10-10**·P1 补）

**债**：内核 `agentSubject` 算 `实例 = 'session-' + String(会话id).slice(0, 8)`。它坏在一个**从未被核实的前提**上：假设会话 id 是**短的无前缀串**。真实形状不是 ⇒ `slice(0, 8)` **恰好等于** `'session-'` ⇒ 实例键**恒为 `session-session-`** ⇒ 审计 / 注册表 / 独立答案里「**哪一个会话**」这一位信息**全丢**。第二半同源：第 1 档（子会话）取**父会话**当实例键 ⇒ 同一个 Lead 起的两个成员子会话算出**同一个**主体 id ⇒ 「独立答案按主体 id 去重」把两个人的卷折成一份、注册表也无法把实例登记到具体某个成员（㉑ 的甲/乙两个修法正需要 `members[<子会话id>]` 这个键）。

**证据（2026-10-10 实测）**

- 公式退化（真 id 直接算）：`session-7fb7087b-c62a-4c64-a6ce-40aab0a78cd9` ⇒ 旧键 `session-session-`；`session-80e3fa83-…` ⇒ 旧键 `session-session-`；**两个不同会话的旧键相同 = true**。
- 真实形状（本机实测，不是猜）：`E:\DSHOME\sessions\` 下 **460 个**会话目录里 **208 个**形如 `session-<uuid>`（例：本任务 Lead 的会话 id `session-7fb7087b-c62a-4c64-a6ce-40aab0a78cd9`）；生成端 `brandString(\`session-${randomUUID()}\`)`（`dsh-api-session-controller/lib/index.js:573/692`、`dsh-headless/lib/index.js:135`）。
- 修后读数（`test/lead-identity.test.js` 的 `B-判据`，两行都原样印出）：
  `[B-读数] 根会话 session-7fb7087b-… ⇒ 实例键 session-7fb7087b-… ; 根会话 session-80e3fa83-… ⇒ 实例键 session-80e3fa83-…`
  `[B-读数] 子会话 session-c1a2b3c4-… ⇒ 实例键 session-c1a2b3c4-… ; 子会话 session-d5e6f7a8-… ⇒ 实例键 session-d5e6f7a8-…`
  ⇒ **两个不同会话 ⇒ 不同键**（根、子两面都测）；**同一会话两次调用 ⇒ 同键**（含「换 header 其余字段仍是同键」）。

**修法**：`components/kernel/lib/index.js` 新增 `会话实例键(会话id)`，返回**会话 id 原样**——不截断、不加前缀、不换父会话；两档（子会话 / 根会话）**统一**用它（兜底值各自保留：`'member-unknown'` / `'lead'`）。

**唯一性论证（三层，都不靠「看起来够长」这种直觉）**

1. **按契约唯一**：`SessionId` 的定义就是「Identifies one session in the store (and its persistence artifacts)」（`dsh-session` lib/types/types.d.ts:4-5）⇒ 它是会话在 store 里的**主键**：唯一性由**身份定义**保证，不由长度保证。
2. **同一会话稳定**：`Session.id` 是 getter，派生自 header 的**唯一一份**拷贝（同包 lib/types/index.d.ts:120-121 "The session identity, derived from its durable header's single copy"）⇒ 同一会话的两次调用必得同一个键。
3. **不截断 ⇒ 不引入碰撞**：任何截断都是把一个唯一键映射到更小的空间上（`slice(0,8)` 就是这个错误的极端形态）。取原样则碰撞面 = 会话 id 本身的碰撞面。

**为什么不加 `session-` 前缀**：真实 id 大多**已经**带它（208/460 实测），再加一层就是修前那种「前缀被自己吃掉」的重复；而 `dsh-agent-loop` 另有一条 `` `${id}-session-${randomUUID()}` `` 的生成式（lib/index.js:1540）⇒ 会话 id **不保证**以 `session-` 开头。**对 id 的形状不做任何假设**，是唯一稳妥的写法。
