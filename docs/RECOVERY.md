# 任务中断后的人工恢复

当前支持查询真源、明确提交回执及显式人工后继。尚未实现原地接管、自动替代任务链或跨进程恰好一次执行。错误中的“已提交”描述业务事实，审计可能仍需补记。

## 先处理部分提交

按故障回执中的项目、任务及事件序号、实例、会审或消息id核对对应账本、登记和 inbox。查询当前事实后再决定恢复；审计失败不能证明业务未发生。宿主已接收不代表已执行，缺接收凭据也不能证明未发送。

`member_spawn` 只完成到登记、绑定或派发时，不再重复创建整个成员。派发事件已经存在就补缺失审计；确认尚未派发且当前授权仍有效，才单独派发。开工书接收未知时先查原 inbox，不直接重发。审批动作成功但完成记账失败时核对原请求和业务真源，批准已占用，不申请一次新批准来盲目重做。

这里的补记是核对后由有权操作者修复账务的要求，尚无自动补记命令；不得手造原主体签名或把模型声明当作人侧确认。

## 失联实例与后继工作

1. 真实 Lead 读取旧任务、冻结判据、依赖、提交成果及相关审计，明确哪些副作用已发生、哪些仍未知。
2. 对旧实例请求 `member_stop`。结果只证明已发中断请求；公共驻留释放也不删除持久子会话。无法确认在途副作用结束时，先核对结果或改用隔离的新输出位置，不在相同路径并发续写。
3. `registry_seal` 旧实例，并回读确认身份已封存，再将旧节点 `task_pending`，理由写明停止/结果未知、保留原结果及后继安排。封存阻止后续新调用，不能撤销已经进入工具体的操作。
4. 确有独立可继续的工作时，Lead 显式 `task_create` 新节点，复制仍适用的冻结判据和原依赖，重新授文件范围、绑定和派发。不要让新节点依赖尚未采纳的旧节点，否则仍会等待旧任务。
5. 通过已有任务书或经历记忆的来源引用记录旧、新两个任务id及接续原因。产物作为来源重新核验；不复制旧人的答案或复核票冒充新人的提交。

已有真实实例绑定的旧任务，不允许另一个同岗新实例借岗位匹配恢复或写入。完全无绑定的历史任务仍按旧岗位寻址，不能用上述组合宣称实例隔离。先由有权操作者核对历史归属，必要时另建明确绑定的新工作。

旧节点保持待决，既没有完成，也没有自动被替代。既有下游对旧id的依赖不会自动改指新id；需要新的任务链时由 Lead 明确重建。原节点终结、结构化后继关系和自动依赖迁移需要另立协议，当前不能通过改状态名冒充实现。

## 仍缺少的宿主事实

当前公开消息接口未提供客户端幂等操作键或可据此核对的持久终局回执。进程在接收之后、取得回执之前退出时，组织侧不能自行证明消息恰好投递一次。自动恢复需要宿主可查询的执行归属、在途操作和可靠安全停点，不能仅凭超时、inactive、封存或释放推断。
