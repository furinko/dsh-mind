## 一、阶段 2：出厂面净化（**净化副本，不改原件**）

### 设计取舍：为什么不直接改 `mind/`

`mind/` 是**正在被使用的心智固件**（本机实例、有 git 历史、被注入器与门禁读）。直接改它 = 动量产文件；
而打包要的是"一份**干净、可分发**的快照"。
⇒ 工具**只读 `mind/`、只写 `packages/dsh-mind/firmware/`**，原件一个字节不碰，**可反复重跑**。

### 工具：`scripts/mind-firmware-build.mjs`

净化的三类（全部**机器可判**，不靠人工挑拣）：

| 类 | 动作 | 判据 |
|---|---|---|
| ① 本机实例件 | **剥离** `L3/`（运行时记忆）、`Project/`（已退役）、`TRASH/` | 运行态记忆不能公开 |
| ② 沿革台账 | **剥离** `L1/changelog-L0.md` / `changelog-L1.md`（约 98KB） | 历史不是规则 |
| ③ 本机读数 | **只报不改**（是否正当由人判断） | `Invariants #13` 出厂卫生 |

### ③ 类的**模式精度**（实测校正，别退回宽模式）

首版 `drive-letter` 写成 `[A-Za-z]:[\\/]`，把 `https://` 的 `s:`、`http://` 的 `p:` 全判成盘符
（4 处命中 3 处是误报）。修正为 **词边界 + 反斜杠**：`(?<![A-Za-z0-9])[A-Za-z]:\\{1,2}`。

**最终扫描结果**：

| 模式 | 命中 | 判定 |
|---|---|---|
| `env-placeholder`（`%APPDATA%`） | 4 处 | ✅ **正当**——环境变量占位符，跨设备可移植 |
| `drive-letter` / `win-user-home` | 1 处（同一条） | ✅ **正当**——`Power.md:33` 是规则里的**举例**（"什么样的算盘符"），`C:\Users\<名>\` 的 `<名>` 是占位符 |

⇒ **实测结论：出厂面无真实本机读数**（`docs/DESIGN.md` §12.2 #8 那条欠账，在固件面上**已闭合**）。

### 产出

- `packages/dsh-mind/firmware/`：**37 个文件 + SOURCE.md，377KB**（剥离 changelog 后从 ~475KB 降下来）
- `scripts/mind-firmware-itest.mjs`：**PASS 9/9**（含 2 条反例：塞 L3 条目 / 塞 changelog 必须报红）

## 二、阶段 3：独立包 `dsh-mind`

### 2.1 为什么是独立包（而不是塞进 `dshome`）

`dshome` 包 = **整个 DSHOME 客户端**（17 host 插件 + 6 client 包 + Electron 壳）。
把心智塞进去，用户装上会**连带得到整个客户端**——那不是"可移植的心智插件"。

**边界判据**：装上本包，你得到的是一套**心智**，不是一个客户端。

| 进 `dsh-mind` | 不进（留在 `dshome`） |
|---|---|
| R0 宪法注入 / R1 上工召回 | 主题皮肤 |
| 写前护栏 / 连接开关 | 命令面板 |
| Skill 触发 / 压缩留痕 / 情绪 / 预算 | 插件中心 / 助手形象 |
| 角色卡子代理 | 输入队列 / 对话卡片化 |
| 出厂固件 + 首启自举 | Electron 壳 |

### 2.2 包结构

```
packages/dsh-mind/
├─ package.json          # dsh.bundle.patch + 14 条 exports + files 白名单（含 firmware/）
├─ cordis.patch.yml      # 自带一层：9 个 insert 行（每行都对应一条 exports）
├─ README.md             # 装机说明 + 数据根解析 + 边界诚实标注
├─ lib/
│  ├─ index.js           # bundle 入口
│  └─ host/              # 13 个文件：9 插件 + 3 共享库（paths/bootstrap/upstream）+ mind-insert
├─ firmware/             # 37 个文件（净化产物）
└─ test/selftest.mjs     # 独立加载自测
```

**关键**：`upstream.js`（上游抗崩层）也搬进来了——它保证**上游改名只是降级、不是崩树**，
这是跨版本可移植的第一道保险。

`verify-dsh-mind-install` 的 12 项覆盖：包已装 / 9 子路径**全部可解析到实体文件**
（漏 exports = 启动崩）/ 固件随包（44 文件）/ **首启自举真落地 + 幂等** / 反例面。

先前只验到"装 + 解析 + 配置树"，**HTTP 那一面未闭合**。补验后：

## 三、补课：能力重叠评估（**由主人质疑驱动**）

### 3.1 我漏掉的那一轴

阶段 0 的摸底只做了**一轴**：「上游有没有这些符号」——量的是**存在性**。
主人一句「官方客户端现在不是有 cron 了吗」戳破了它：

> **符号在 ≠ 能力不重叠。**

这正是 `verify-integrity` 配方 ⑭① 的「**判据漏轴**」：判据只覆盖维度 A（符号），
维度 B（职责/作用域）从没进过判据 ⇒ 一份"上游有什么"的清单**读起来像"上游能替代"**。

### 3.2 ⚠️ 三次误判的订正（**这段比结论更重要**）

补课过程中我**连错三次**，根因是同一个：**拿二手信息推断能力**。

| # | 我当时的结论 | 依据（错的） | 事实 | 怎么被推翻 |
|---|---|---|---|---|
| 1 | 「上游 `dsh-client-ui-schedule` 是 **Read-only** 目录，不是面板」 | `package.json` 的 **description** 原文 | 它是**一级侧边栏入口「自动化任务」**，带列表/筛选/搜索/详情/**运行记录**/删除 | 主人**截图** |
| 2 | 「官方 schedule 与自建 cron **no-overlap**（官方只在会话内）」 | `dsh-schedule` 的 description "over the **session** event log" | 官方到点**拉起独立新会话**——与自建同形态 | 主人**亲验** |
| 3 | 「它带完整 cron 表单（`cronForm.monthly/weekly/…`）」 | 在 asar 里搜到这些**文案 key** | 那些 key 是**详情页渲染规则**用的，不是编辑表单；「+ 新建」**不弹表单**（直接拉起会话） | 主人**亲验** |

**三个共同根因**：

1. **用包 description 判断能力** —— 上游自己的描述与实现不符（#1、#2）。
2. **样本偏差** —— 只查 `E:\DSHOME\node_modules`（0.1.5-rc.2 的依赖），
   **没查主人实际运行的桌面版 runtime**（`runtime.json` 的 `desktopVersion: 0.2.0-rc.1`）。
   真正的实现 `dsh-experimental-schedule-bundle` **本地根本没装** ⇒ 我的"上游没有"是**没看到**，不是**不存在**。
3. **看到符号就推断能力** —— 搜到 `cronForm.*` 就假设有表单 UI（#3）。

**判据（已写进 `verify-mind-vs-upstream.mjs` 的条目注释）**：
> **不许用包 description 判断能力；必须实测运行中的系统。**

这是本仓 `prompt-surface-audit` 卡里那条"**别信注释里的『实测』**——机制代码与活进程读数才是一手"的**同型复发**。

### 3.3 机器化：`scripts/verify-mind-vs-upstream.mjs`

对 8 个自建件逐条列出上游同类包（**读包 description 作可复核依据**），强制写明重叠判定与依据；
**判不出就写 `unevaluated`，门禁据此判红**（"没评过"不许静默当通过）。

**处置分档**（2026-09-29 加）：
- `unevaluated` ⇒ **判红**（不许静默）
- `replaced`（上游可替代）⇒ **必须有 `retirePlan`**，否则判红；有计划则挂账不红
  —— **"有计划的挂账 ≠ 静默放过"**

### 3.4 评估结论（8/8）

| 自建件 | 上游同类 | 判定 |
|---|---|---|
| **`cron.cjs`（62KB）** | `dsh-experimental-schedule-bundle` | ✅ **上游可替代 ⇒ 退役**（主人拍板，见 §3.5） |
| 面板（可管理） | 官方「自动化任务」 | ⚠️ 部分——**cron 管理面应退役**（官方已覆盖） |
| `/api/mind/todos` | `dsh-tool-todo` | ⚠️ 部分——上游是**会话内执行清单**，自建是**跨会话项目台账** |
| 护栏 | `dsh-experimental-auto-review` 等 | ⚠️ 部分——上游管**工具授权**，自建管**内容与区域** |
| R0/R1 注入 | `dsh-agent-instructions` / `dsh-persona` | ❌ **不可替代**——上游供**通道**，自建供**内容与策略** |
| Skill 触发 | `dsh-skill-filesystem` | ⚠️ 部分——**风险面**：两条路都扫目录，已写守卫 |
| 角色卡 | `dsh-experimental-tool-agent-team` | ⚠️ 部分——上游按 Team membership 装同一套；自建**每成员独立 persona** |
| 情绪/预算/压缩留痕 | `dsh-token-meter` 等 | ❌ **不可替代**——上游供**底层信号**，自建定**策略与呈现** |

**共同规律**：**上游供能力与通道，自建供内容与策略。**

### 3.5 cron 退役决定（**2026-09-29 主人拍板**）

**官方的「自动化任务」与自建 `cron.cjs` 是同一件事，且官方更完整**：

| 能力 | 官方 | 自建 |
|---|---|---|
| 到点拉起**独立新会话** | ✅ 主人亲验 | ✅ |
| 任务列表 / 状态筛选 / 搜索 | ✅ | ❌ |
| **运行记录** | ✅ 含保留策略、分页 | ⚠️ 裸 jsonl |
| 创建方式 | 自然语言（会话内 `schedule_create`） | ⚠️ 手写 JSON |

**决定**：`dsh-mind` v1.1 **不做 cron**——面板（236KB）与引擎（62KB）都不进包，
仅保留 `cron-recipes.cjs`（9KB，**自治"处方"**＝该预置哪些自维护任务，属心智产品决策，官方无对应）。

**未查实项（不假装查过）**：官方是否有**串行闸 / 重试上限**。
但该未知项**不改变决定**——若有＝纯重复；若无＝缺的是并发保护，应以**提上游 issue** 解决，
而非让一个"可移植"的包去背 62KB 引擎。

**门禁已钉住该决定**：`verify-mind-vs-upstream.mjs` 把 `cron.cjs` 判为 `replaced` 并带 `retirePlan`
⇒ 改判必须动文件（不是靠记忆）。
