# concurrent-writers — 多写者共享工作区的纪律

> 心法一句话：**"工作区干净"不等于"没有别人"——并发的另一半可能就是我自己。**
> 来源：L3 结晶「并发改配置炸整树」（私有区，不推送）·（多会话并行改同一 profile 配置 ⇒
> 后端 **38 轮崩溃循环**）+ Learn 的 git 竞态条目（`add` 完还没 `commit`，另一会话把我的文件一起提交了）
> + 2026-09-14 自治会话并发写同一批文件（落地 `cron.cjs` 串行闸）。

## 一、使用流程（Step 1→N）

1. **先盘点写者**：动手前问一句"**还有谁在动这批文件**"——`git status` 干净**不能**当作"没有并发写者"（别人可能刚提交完；也可能是**我自己的另一个会话**或正在跑的自治任务）。机器件＝`node scripts/git-writer-probe.mjs`（一次盘点：「暂存面」vs「在飞的其它面」+ 硬信号；`--wait --until <路径> --timeout 6h` 等对方落定，退出码 0 无风险 / 1 用法错 / 2 提交会撞 / 3 超时）。⚠️ **它只是探针，不是闸**。**归属维度（1.0.4 加）**：探针读 `mind-private/tasks/write-log.jsonl`（`dshome-mind-guard` 在 write/edit **写成功**后追加的 `{ts,session,tool,path}`），给每条在飞行标 `← 会话 @ 时刻`，并检出**同一文件被 ≥2 个会话在窗口内写**（默认 30m，`--claim-window` 调）——那才是"同时改同一个东西"的可检出信号。台账不存在时如实报"归属维度不可用"（不猜、不编）。
2. **先找现成的闸**：仓里/系统里有没有锁、队列、串行闸、事务？（本仓先例：`cron.cjs` 的自治串行闸按序排队；台账一律 **append-only**；改"自我类"文件前先 `evolve-log snapshot`。）**有就复用，别自造。**
3. **共享配置＝单写者**：主 profile 的 `cordis.patch.yml`、`package.json` 的 `bundles`、`pnpm install` 这类**同一时刻只允许一个写者**。要并行 ⇒ **各自独立环境**（独立 `DSH_HOME` + 独立端口 + 独立目录），实验完就停。
4. **优先追加语义**：能用 **append-only** 就别"读-改-写"（两个写者各自读、各自写 ⇒ 后写覆盖前者，双方都不知道）。确需读-改-写时，写前重读 + 带版本/时间戳判别。
5. **git 竞态**：`add` 与 `commit` 之间别停太久；提交前用 `git diff --cached --stat` **复核只包含我该提交的**——发现别人的在飞文件就**排除**，并在汇报里点名"哪些是别人的"。⚠️ **归属的边界要说准**（1.0.4 收窄）：探针能标**"谁 `write`/`edit` 过它"**（读 `write-log` 台账），但**仍判不了"谁 `git add` 的"**——`add` 是 index 操作、不经过工具层 ⇒ 台账里没有它。所以"暂存面归属待核"这句**依然有效**，只是从"完全不知道"收窄成"知道谁写的、不知道谁暂存的"；三个独立写者面里**只要有一个是别人的，就别全量 `commit`**（改用选择性提交或等落定）。
6. **拿不到闸 ⇒ 响亮失败**：不许静默降级成双写/裸写；冲突要么排队、要么报错退出。
7. **善后先判"谁覆盖了谁"**：拿 mtime / 账本 / sha / 提交历史判**谁覆盖了谁**，再决定重放或回滚；**别直接再写一遍**（那会把覆盖痕迹埋掉）。
8. **收口写清楚**：记录"我知道可能有谁在写""我排除了哪些别人的文件""我用了什么闸"。

## 二、核心规则（硬约束）

- **单写者协议**：共享配置/共享账本同一时刻只有一个写者；并行必须在**独立环境**里做。
- **"干净"不是"无写者"**：不把 `git status` 干净当成安全信号。
- **append-only 优先**，读-改-写是竞态温床。
- **提交前必看 staged**：`git diff --cached --stat`；别人的改动**不卷入**。
- **闸拿不到就失败**，不许静默降级。
- **善后先判覆盖关系**，再谈重放/回滚。

## 三、行为准则（软技能）

- 动手前**看痕迹**：目录里有别人留下的改动（探针目录被加过包、配置文件被改成注释块）就立刻换独立环境。
- 冲突发生后**先认再看**：先固定事实（谁先写、覆盖了什么），别先解释。
- 汇报里**点名归属**：我的 / 别人的 / 不确定的，分列清楚（"不确定"也要写）。
- 一次只动一个共享面（别同时改配置与依赖）。

## 四、踩坑记录（每条 ≤100 字）

- **多会话并行改同一份主配置 ⇒ 后端 38 轮崩溃循环**（16:22–16:45）：我在改 `cordis.patch.yml` 加官方实验三包，另一会话正改 `dsh.profile.bundles` + `pnpm install`；两边各自"合法"，合起来挂不上 ⇒ 靠外部救援方回退一行才稳。
- **"工作区干净"被我当成"没有并发写者"**——那次并发的另一半**就是我**（另一个会话也是我）⇒ 现在的判据：先问"还有谁"，别只看状态。
- **git 竞态**：我 `add` 完还没 `commit`，另一会话把我的文件一起提交了 ⇒ **提交前必须 `git diff --cached` 复核**。
- **自治会话并发写同一批文件**（两条 cron 任务 `catchUp` 同时拉起 + 第三个会话在跑）⇒ 落地 `cron.cjs` **串行闸**（忙则排队、放闸唤醒、去重、超时兜底）并配 itest。
- **并发会话的在飞文件不该被"顺手修"**：同仓库另一会话的未提交改动（配置文件/脚本）既不卷进我的提交，也不替它改。
- **两个写者同时点红「本地快照」也算并发**（2026-09-23 实测）：`build-stage/payload` 这类 **git 之外**的快照面不受 git 保护——A 暂存着自己的改动、B 在写新包，`verify-payload` 同时报三件陈旧（两件 A 的、一件 B 的）⇒ 谁先提交谁就得把快照同步成"含对方 WIP"，提交前先跑探针。
- **`add` 与 `commit` 之间的 index 会被第三方改写**（2026-09-23 实测）：17:48 暂存面只有自己的 2 件，17:51 变 6 件（多出另一会话的 4 件）⇒「我 add 过」不是提交依据，`commit` 前必复核 `git diff --cached --name-only`。
- **"两个会话改同一份文件"≠ 都会丢内容——先分三类**（2026-09-23 实测，`cron.cjs`）：① **读-改-写覆盖**（双方各自读到旧版，后写者**全量覆盖**）⇒ 会**静默丢**；能这么干的通道**只有 `write`**（`edit` 要 `old_string` 精确匹配当前内容 ⇒ **天然 CAS**，撞了直接失败报错，不会静默）；② **各改不同区域**（他改 127 行、我改 184/353 行）⇒ **不丢内容**，git 本可自动合并，麻烦的是**归属分不开**（一份 `git diff` 里两个人的东西）⇒ `git apply --cached` **只暂存自己的 hunk**（本次实证：7 hunk 里 1 个是他的，剔掉后 `attachSession` **0 处**进 index）；③ **改同一区域** ⇒ 必冲突，只能靠协调 / 排队。
  ⇒ **别把"并发会话"当问题，也别把"加锁"当唯一解药**：② 类要的是**归属可见**（`write-log` 台账 + 探针归属维度），① 类才要**版本校验**。两类的解药不同——混为一谈就会去修错的那个。
